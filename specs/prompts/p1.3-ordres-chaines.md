# Prompt P1.3 — Parser des chaînes d'ordres

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Les modèles métier existent (internal/models : GameState, Territory, Army,
Noble, enums), la génération de carte est en place (internal/engine/mapgen,
endpoint /api/map). `Army` est l'unique entité de force présente sur un
territoire ; son champ `Size` compte des troupes abstraites. Il n'existe pas
d'entité `Troop` ni de `TroopID` dans le modèle.
Références : specs/gdd.md (section 6) et specs/architecture.md
(SECTION 6 — "Format des chaînes d'ordres (texte)" : le format y est décrit
précisément, suis-le à la lettre).

PÉRIMÈTRE : cette tâche couvre le PARSER, le MODÈLE des ordres/chaînes et la
RÉCEPTION des chaînes. La PROGRESSION des chaînes (qui doit prendre en compte
TOUTES les chaînes d'ordres pour résoudre combats, retraites et jonctions)
est la tâche P1.4 : ne l'implémente pas, mais prévois l'interface.

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. Format texte (décrit dans architecture.md §6, à implémenter tel quel) :
   - En-tête : code trigramme du noble émetteur (ex. "JEA # Jean",
     le reste après # est un commentaire)
   - Une ligne par ordre, la POSITION de l'armée est TOUJOURS explicite :
       XXX A YYY      (attaque/atteindre, YYY adjacente)
       XXX S YYY      (soutien DÉFENSIF : l'armée de XXX soutient la tenue de
                      l'armée en YYY — YYY adjacente, YYY ≠ XXX)
       XXX S YYY - ZZZ (soutien OFFENSIF : l'armée de XXX soutient l'attaque
                      de l'armée de YYY vers ZZZ — ZZZ adjacente à XXX,
                      YYY–ZZZ adjacentes)
       H XXX          (maintien sur XXX = position de l'armée)
       XXX J YYY      (jonction, déplacement PACIFIQUE vers YYY adjacente —
                      TOUJOURS en DERNIER ordre d'une chaîne)
       P XXX          (pillage, XXX = case où l'armée se trouve)
       XXX O YYY      (otage : YYY = code du noble prisonnier de l'armée de
                      XXX, passé au statut `hostage` — GDD §4/§6)
       XXX K YYY      (cachot : même syntaxe, passé au statut `dungeon`)
       XXX D XXX YYY ZZZ ...   (dispersion : XXX = position, puis UNE
       destination par troupe abstraite de l'armée — nombre de destinations =
       taille de l'armée ; la case de l'armée est une destination valide, listée
       explicitement ; destinations adjacentes ou égales à la position ;
       répartition des NOBLES par ASTÉRISQUE : `XXX*` = tous les nobles en
        XXX, `YYY*JEA` = Jean en YYY, `YYY*JEA*ANN` = Jean et Anne en YYY ;
        le suffixe `*` seul dans `XXX*` = tous les nobles restants ; chaque
        noble au plus une fois)
   - Sans parenthèses = liaison SINGLE ; entouré de parenthèses = BOUCLE
     ("(ATL S NOR)" = boucle, "BRI A ATL" = single) — chaque transition a
     SA propre liaison
   - Insensible à la casse (normalisé en MAJUSCULES), lignes vides ignorées,
     commentaires # ignorés, codes vérifiés contre la carte, erreurs avec
     numéro de ligne et code d'erreur

2. Modèle (internal/models) :
    - Order { ID, Type (OrderType), ArmyID (vide après le parsing puis fixé à
      la réception), PositionID TerritoryID (la case où l'armée doit être),
      TargetIDs []TerritoryID (cibles territoriales de A/S/J/D),
      NobleTargetIDs []NobleID (unique cible noble résolue de O/K),
      NobleAssignments map[TerritoryCode][]NobleCode (dispersion uniquement :
      répartition par astérisque), Liaison LiaisonMode }
    - LiaisonMode : single | loop, PORTÉ PAR L'ORDRE (chaque transition)
    - Chain { ID, NobleID, ArmyID (fixé à la réception : la chaîne est portée
      par l'unique armée présente sur le territoire de réception et s'applique
      à TOUTES ses troupes abstraites, jamais à des ordres mixtes), Orders
      []Order, CurrentIndex int }
    - OrderType : attack | support | hold | join | pillage | disperse |
      hostage | dungeon
    - `Army.ChainID *ChainID` est le lien inverse vers la chaîne portée ; PAS
      de champ ArmyStatus : l'armée est "Sans Ordre" quand `Army.ChainID == nil`.
      `GameState.Chains []Chain` stocke les chaînes et `NextChainID int` alloue
      des identifiants globaux `C1`, `C2`, ... persistants ; les IDs `O1`,
      `O2`, ... sont locaux à une chaîne.
    - `Noble` conserve `LocationID` : avec au plus une `Army` par territoire,
      ce territoire permet de retrouver l'armée chevauchée sans ajouter de
      `Noble.ArmyID`. Le geôlier est dérivé du propriétaire de l'armée présente
      sur ce `LocationID` et n'est pas dupliqué dans le noble. L'absence d'armée
      ne rend pas le `LocationID` invalide : un noble peut rester seul après la
      destruction de son armée sur une case vide ou alliée.
    - `Noble.Status NobleStatus` a exactement les valeurs `free`, `hostage` et
      `dungeon` ; `hostage` et `dungeon` sont les deux états regroupés sous le
      terme "prisoner". Un noble prisonnier ne peut pas émettre de chaîne.
      `Noble.LastEmissionTurn int` mémorise la dernière émission (zéro = aucune
      émission) pour appliquer une émission par noble et par tour, même après
      remplacement de chaîne.
    - `NobleTargetIDs` corrige l'ambiguïté de O/K : `TargetIDs` ne contient que
      des territoires ; le trigramme noble de `XXX O YYY` ou `XXX K YYY` est
      résolu dans l'unique entrée de `NobleTargetIDs`. La syntaxe texte O/K ne
      change pas.

3. Validation statique (fonction pure ValidateChain(game, chain) →
   []validationError) :
    - Les niveaux suivants restent distincts : le parser vérifie la syntaxe et
      résout les codes ; cette validation vérifie les références, adjacences et
      contraintes intrinsèques ; la réception vérifie l'émetteur et l'armée
      réceptrice ; l'exécution P1.4 vérifie l'état du monde devenu effectif.
    - Références valides : noble existe, territoires existent, la position de
      chaque ligne est un territoire valide
    - Adjacence : pour A/J, la cible est ADJACENTE à la position ; pour le
      soutien DÉFENSIF, YYY adjacente à XXX et YYY ≠ XXX ; pour le soutien
      OFFENSIF, ZZZ adjacente à XXX ET YYY–ZZZ adjacentes ; pour D,
      chaque destination est adjacente OU égale à la position
    - Structure : J ne peut figurer qu'en DERNIER ordre de la chaîne (un J
      suivi d'un autre ordre → erreur de validation)
    - Contraintes par type :
      - H/P : le territoire indiqué est la position de l'armée (exactement)
      - P : pas de cible supplémentaire (le pillage cible la case de l'armée)
      - O/K : la cible est un CODE de noble (trigramme), résolu dans un unique
        `NobleTargetIDs`, et le noble existe
      - D : la validation statique vérifie le format, les destinations et les
        astérisques ; le nombre de destinations dépend de `Army.Size` et est
        vérifié à la RÉCEPTION
      - S : cibles présentes, adjacences selon la forme (ci-dessus)
    - Les validations liées à l'état du monde au moment de l'EXÉCUTION
      (position devenue fausse, case libre ou occupée, infrastructure présente,
      combat, résultat d'un ordre précédent, cible O/K devenue différente...)
      relèvent de la résolution P1.4 (failure/invalid) : ne les anticipe pas
      ici, mais prévois les types d'erreur.

4. Réception de la chaîne (AssignChain(game, chain) → error) :
    - La chaîne est reçue par l'ARMÉE présente sur la POSITION de la
      PREMIÈRE ligne (pour H/P, le territoire après le symbole) ; elle est
      portée par cette armée et s'applique à TOUTES ses troupes abstraites.
    - Aucune armée du joueur émetteur sur cette position, ou une armée d'un
      autre joueur → erreur de soumission propre.
    - La nouvelle chaîne REMPLACE la précédente (il n'existe PAS de
      modification de chaîne).
    - Capacité : 1 ÉMISSION par noble et par tour (le remplacement compte
      comme une émission). Un noble `hostage` ou `dungeon` ne peut émettre
      aucune chaîne ; `LastEmissionTurn` interdit une seconde émission au même
      tour.
    - À la réception : validation du nombre de destinations de D contre
      `Army.Size`, répétitions comprises, et couverture des NOBLES qui
      chevauchent l'armée (tous assignés par astérisque, prisonniers compris,
      sinon ordre INVALIDE — GDD §6).
    - Pour un ordre O/K exécutable immédiatement sur la position de réception,
      la cible doit être prisonnière, co-localisée et détenue par le propriétaire
      de l'armée. Un O/K portant sur une position future est revalidé par P1.4.
    - Aucune mutation ne survient avant que tous les contrôles de réception
      passent. Au commit : supprimer l'ancienne chaîne de l'armée, allouer le
      `ChainID`, renseigner `Chain.ArmyID` et chaque `Order.ArmyID`, mettre à
      jour `Army.ChainID`, `GameState.Chains`, `NextChainID` et
      `Noble.LastEmissionTurn` atomiquement.

5. Parser (internal/engine, ex. package orders) :
   - ParseChain(text string, game) → (Chain, []ParseError) : erreurs
     COLLECTÉES (toutes les lignes signalées), chaque erreur avec n° de
     ligne, type d'erreur (unknown_symbol, invalid_code, missing_target,
     too_many_targets, bad_header, no_header, noble_not_found,
     unclosed_parenthesis...), message en anglais
    - Gère parenthèses, commentaires #, casse, espaces multiples, ligne vide
     - La chaîne parsée n'est PAS encore assignée (AssignChain séparée) :
       le parser retourne une chaîne sans ArmyID ni ChainID définitif,
       l'assignation remplit ArmyID et valide les contraintes de réception

6. Sérialisation : chaînes et ordres survivent au round-trip JSON de
   GameState (tests inclus), avec `Army.ChainID`, `NobleStatus`,
   `LastEmissionTurn`, `GameState.Chains` et `NextChainID`.

7. Projection de développement (`StateView`, `/api/state`) :
    - Chaque armée de la vue expose `chain`, soit `null` si
      `Army.ChainID == nil`, soit la chaîne courante sous cette forme : noble
      émetteur, `currentIndex` et ordres dans leur ordre source.
    - La vue n'expose ni `ArmyID` ni `ChainID`. Les ordres utilisent les codes
      publics : `position` et `targets` pour les territoires, `nobleTargets`
      pour O/K et `nobleAssignments` pour D.
    - `NobleView` expose au minimum `code` et `status` afin d'adresser un noble
      et de rendre sa captivité explicite.
    - Cet endpoint de développement n'a pas d'identité de joueur : `players`
      indique seulement un nombre de joueurs. Il expose donc TOUTES les chaînes
      sans filtrage. Cette exception dev ne fixe pas la politique de vue privée
      de P2.2/P2.2a/P3.2.

8. Tests (internal/engine/orders_test.go ou équivalent) :
   - Parser : chaque règle du point 1 (exemples exacts du format dans
     architecture.md §6), cas limites (sans en-tête, symbole inconnu, code
     inexistant, cible manquante, parenthèse non fermée, D sans destination,
     casse mixte, commentaires, lignes vides)
    - Validation : chaque contrainte du point 3 (cas OK + cas KO — y compris
      J suivi d'un ordre → erreur, soutien offensif/défensif : adjacences,
      YYY ≠ XXX)
     - Réception : pas d'armée du joueur sur la position de la 1re ligne →
        erreur ; remplacement d'une chaîne existante ; capacité
        1 émission/noble/tour (2e émission refusée) ; émission d'un noble
        `hostage` ou `dungeon` refusée ; D avec nobles présents non tous assignés →
        ordre invalide
    - D : nombre de destinations ≠ taille de l'armée → erreur à la réception
     - O/K : noble inconnu → erreur de validation ; cible non prisonnière,
       non co-localisée ou détenue par une autre armée à la réception → erreur
       (cas KO) ; cible prisonnière de l'armée → ordre valide (cas OK) ; cible
       d'une position future revalidée par P1.4
    - JSON round-trip, y compris chaînes, statuts de noble et compteur de chaînes
    - StateView : chaîne projetée sous l'armée, `chain: null` sans chaîne,
      codes publics sans IDs internes et exposition dev non filtrée

Critères d'acceptation :
- make test passe ; make vet passe ; aucune dépendance tierce ajoutée
- L'interface de résolution est prête pour P1.4 : documente la signature
  prévue (ex. Resolve(game) traitant toutes les chaînes simultanément et
  produisant des outcomes success/failure/invalid par ordre, puis appliquant
  les règles de progression single/loop) sans l'implémenter

Note : signale dans ta réponse finale toute évolution des specs nécessaire
(ne modifie pas les specs toi-même). Ne commite pas : je m'en charge.
```
