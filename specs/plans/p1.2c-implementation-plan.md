# Plan P1.2c — Nommage : communes partout, affinité de terrain, trigrammes

Brief d'exécution autonome pour un modèle d'implémentation.

## Contexte

P1.2a (vocabulaire troupe/armée) et P1.2b (lieux-dits → villages) sont faits. La génération de
carte existe (`internal/engine/mapgen`), le loader d'assets aussi
(`internal/db/assetgen`, `assets/{communes,prenoms,qualificatifs}.csv`), le contrat map.json est
décrit dans `specs/architecture.md`. P1.2c acte le système de nommage final :

- TOUT territoire porte un nom de commune de `assets/communes.csv` : plus de
  `"{Qualificatif} de {Commune}"`, plus de "Forêt de Rosemont", plus de "Vallées de...".
- Chaque commune est associée à un TERRAIN DE PRÉDILECTION (`plain|forest|hill|mountain|swamp|any`) ;
  l'assignation favorise l'affinité, avec repli déterministe seedé.
- Les codes de territoires sont des TRIGRAMMES partout (3 lettres) : fin du schéma 3/4 lettres.
- `assets/qualificatifs.csv` et tout son support (loader, tests, log serveur, `isBorder`) sont
  supprimés.

Le prompt source est `specs/prompts/p1.2c-nommage-communes.md` — lire ce fichier en entier avant
de commencer. Références : `specs/gdd.md` (§3), `specs/roadmap.md` (P1.2 détaillé item 7),
`specs/prompts/p0.2-assets-csv.md` et `p1.1-modeles-metier.md`.

Règles absolues :

- Code exclusivement en anglais ; seules les chaînes de contenu de jeu sont en français.
- Aucune règle de jeu modifiée : diff des specs = substitution de vocabulaire + reformulation

## Difficulté et modèle recommandé

Difficulté **3/5** — un algorithme de nommage modéré (buckets + repli déterministe), des
suppressions mécaniques (qualificatifs), mais un volume de contenu CSV élevé (~450 communes,
unicité codes/noms vérifiée à la main puis par le loader) et des invariants touchés dans 3
suites de tests (assetgen, mapgen, models). Le risque est l'INCOHÉRENCE (une référence à
`Qualificatif` oubliée, un code 4 lettres resté dans un fixture). Vérifications finales
automatisées (§ Vérifications) non négociables. Modèle intermédiaire suffisant (ex. Claude
Sonnet 4.5, GPT-5-Codex) : la seule vigilance réelle est la génération du CSV — les tests du
loader font office de filet de sécurité.

## Décisions de conception (à appliquer et documenter)

1. **`type Commune struct { Code, Name, Terrain string }`** dans assetgen. `Terrain` reste un
   `string` (le package reste stdlib-only, comme aujourd'hui) ; les 6 valeurs autorisées
   réutilisent la map `validTerrains` existante. `Asset` survit pour les prénoms.
2. **Couverture des affinités = erreur dure de `Load()`** (arbitrage utilisateur, lecture stricte
   de « cohérence » du prompt) : après la validation ligne à ligne, `Load` échoue si l'un des 6
   buckets (5 terrains + `any`) est vide. Garantit inconditionnellement la contrainte de
   couverture mapgen ; les fixtures de tests valides doivent couvrir les 6 affinités.
3. **Algorithme de nommage en 2 phases** (déterministe, seedé via `newRNG(seed, "naming")`) :
   - Partition des communes en 6 buckets par affinité, chaque bucket **mélangé** avec le rng ;
     tirage = pop en fin de slice (O(1)).
   - **Phase 1 (couverture)** : pour chaque terrain dans l'ordre fixe `plain, forest, hill,
     mountain, swamp`, s'il existe un site de ce terrain, nommer le site non encore nommé
     d'index le plus bas avec le prochain tirage du bucket de même affinité → « au moins une
     commune de chaque affinité utilisée si la carte contient ce terrain » satisfait par
     construction.
   - **Phase 2** : sites restants en ordre d'index — priorité 1 : bucket du terrain du site ;
     priorité 2 : bucket `any` ; **repli** : premier bucket non vide dans l'ordre fixe
     `plain, forest, hill, mountain, swamp, any`. Erreur si tout est épuisé.
   - Unicité des codes et noms sur la carte = conséquence de « chaque commune utilisée au plus
     une fois » + unicité garantie par le loader.
4. **`validateAssets(assets, cfg.SiteCount)`** : exige `len(communes) >= SiteCount` (désormais
   CHAQUE territoire est nommé — c'est le changement clé vs l'ancien `VillageCount`) + garde-fous
   trigramme/nom/terrain/unicité. Les contrôles qualificatifs disparaissent.
5. **Suppressions dans `naming.go`** : `isBorder`, `compatibleQualifiers`, `orderedVillages`,
   `sortLieuSites`, `isPrefix`, `isQualifierTerrain`, import `sort`. **Conservés** : `isTrigram`,
   `assignVillages`, `squaredDistanceToChosen`. Nouvelle signature :
   `nameTerritories(rng *rand.Rand, assets assetgen.Assets, terrain []models.Terrain) ([]nameCode, error)`
   — plus besoin de `villages`, `polygons`, `centroids`, `edges`, `cfg`.
6. **Modèles** : invariant territoire = `isCode(t.Code, 3)` uniquement, message
   `(want exactly 3 uppercase letters)` (aligné sur la formulation noble existante) ; commentaire
   transitoire P1.2b remplacé par la règle finale.
7. **Docs** : périmètre = fichiers listés par le prompt + `architecture.md` (contrat map.json,
   mentionné au §3 du prompt) + `.opencode/AGENTS.md` (doc vivante, 2 passages devenus faux) +
   retouches minimales des prompts p0.1/p0.3/p1.2b/p1.6 (arbitrage utilisateur). `specs/plans/*`
   et `p1.2-generation-carte.md` restent historiques.

## Étape 1 — Assets (`assets/communes.csv`)

Réécriture complète au format `code;nom;terrain`, **~450-470 communes** (cible spec : 400-500).

- **Conserver les 200 existantes**, affinité par famille morphologique :

| Famille | Affinité | Exemples |
| --- | --- | --- |
| `Bois*`, `*bois` (`Châteaubois`, `Pontbois`, `Valbois`), `Sauveterre` | `forest` | Boisclair, Boisvert |
| `Mont*` | `mountain` | Montauban, Montfort, Montchêne |
| `Roche*`, `Val*` (vallées → coteaux), `Beaumont` | `hill` | Rochefort, Valmont |
| `Pré*` | `plain` | Préclair, Préval |
| `Bourg*`, `Ville*`, `Maison*`, `Saint*/Sainte*`, `Château*` (sauf Châteaubois), `Pont*`, `Font*`, `Bel*`/`Beau*` (sauf Beaumont), `Clair*`, `Clos*`, divers (`Rosemont`, `Orval`, `Griffecourt`…) | `any` | Belval, Belvent |

- **Ajouter ~250-270 nouvelles** pour équilibrer les buckets (l'existant donne ~0 swamp et ~115
  `any`) — composés médiévaux plausibles évoquant leur terrain de prédilection :
  - `swamp` (~50) : Fougères, Maraisclair, Fangeval, Bourbelong, Les Saules, Tourbeval, Jonclaire,
    Roseauval…
  - `plain` (~75) : Beaupré, Vergers, Champlong, Bléval, Beauchamp, Prélong, Meunecourt…
  - `forest` (~70) : Chênevaux, Chêneraie, Hêtrevaux, Boischamp, Charmoy, Forterre…
  - `hill` (~30) : Bruyères, Puyvert, Cotelard, Costebelle…
  - `mountain` (~40) : Mont-Dore, Montsoreau, Montperdu, Rochemaille, Cimebelle, Piclong…
- **Distribution cible finale** : plain ~85, forest ~85, hill ~65, mountain ~65, swamp ~50,
  any ~115 (total ~465).
- Invariants : codes trigrammes `A-Z` uniques (dériver des consonnes pour les composés :
  Mont-Dore → `MDO`, Beaupré → `BPR`, Chênevaux → `CHV`), noms uniques, en français. Le loader et
  ses tests valident le tout.
