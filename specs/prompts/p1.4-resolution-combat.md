# Prompt P1.4 — Moteur de résolution : progression, mouvement, combat & retraites

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le parser et les modèles d'ordres/chaînes existent (P1.3, internal/models +
package de parsing), la génération de carte est en place (internal/engine/mapgen).
Références : specs/gdd.md (§5 Combats, §6 Retraites, §8 Contrôle territorial)
et specs/architecture.md (§6 — sémantique des ordres et progression, à suivre
à la lettre).

PÉRIMÈTRE : la résolution simultanée des ordres de TOUTES les chaînes, les
combats, les retraites, le contrôle territorial et la progression des chaînes.
Le RAVITAILLEMENT/famine (P1.5), l'HIVER (P1.6) et la transmission différée
(P2) sont HORS périmètre (vision T0 au MVP) : le moteur est conçu en phases
pour s'y brancher.

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. Interface (internal/engine) :
   - Resolve(game *models.GameState) (Resolution, error) — fonction PURE,
     déterministe, sans I/O (aucune lecture d'horloge, d'aléa ou de global)
   - Resolution : contient des EVENTS structurés (outcomes par ordre,
     combats, retraites, fusions, pillages, dispersions, changements de
     contrôle) que la tâche P1.7 formatera en TurnReport — pas de formatage
     ici
   - Architecture en PHASES (ordre du GDD §2, tronqué au périmètre) :
       Phase 1 — Exécution des ordres (toutes les chaînes, simultanément)
       Phase 2 — Combats (cases contestées)
       Phase 3 — Retraites
       Phase 4 — Progression des chaînes + contrôle territorial
     Des points d'extension clairs pour insérer ravitaillement (P1.5) et
     propagation (P2). Itération DÉTERMINISTE : armées par matricule
     croissant, territoires par ID.

2. Phase 1 — Exécution des ordres (un ordre courant par armée, toutes les
   chaînes à la fois) :
   - POSITION EXIGÉE : l'armée absente de la position de l'ordre → failure
     (single : brise ; loop : retente)
   - A (attaque/atteindre) : déplacement vers cible ADJACENTE. Case vide →
     succès, l'armée s'y déplace. Case occupée par un ALLIÉ → failure (on
     n'attaque pas un allié). Case occupée par un ENNEMI → combat (Phase 2)
   - J (jonction) : déplacement pacifique vers cible ADJACENTE. Case vide →
     succès. Case occupée par un allié (déjà présent ou arrivé ce tour par
     A/J) → FUSION (la pile devient N armées). Case occupée par un ennemi →
     failure
   - D (dispersion) : chaque destination ADJACENTE ou = position. À
     l'exécution, chaque destination doit être LIBRE et NON CIBLÉE par une
     attaque ce tour : l'armée correspondante s'y déplace (ou reste si c'est
     sa case). L'armée d'origine (celle qui porte la chaîne) prend la
     PREMIÈRE destination listée ; les autres armées sont CRÉÉES (matricule
     suivant — prévois un compteur dans GameState si nécessaire, documente
     l'évolution). Toute destination non résolue → ordre non résolu
     intégralement
   - P (pillage) : cible = la case de l'armée. Détruit UNE infrastructure de
     la case (la plus récente) + bonus R (constante moteur, défaut : 2).
     AUCUNE infrastructure → invalid (brise immédiatement, les deux modes)
   - S (soutien défensif) : soutien à l'armée ALLIÉE occupant la cible
     ADJACENTE. Sans allié sur la cible → failure. Effet appliqué en Phase 2.
     Si la cible n'est pas attaquée ce tour, le soutien est gaspillé mais
     l'ordre réussit
   - H (maintien) : succès immédiat, l'armée reste
   - INVALIDE à l'exécution (cible non adjacente, armée disparue entre
    -temps, P sans infrastructure...) → invalid (brise immédiatement, les
     deux modes)

3. Phase 2 — Combats (chaque case contestée : attaquants vs occupants) :
   - Force d'attaque : 1 par armée ; les armées ALLIÉES ciblant la même case
     FUSIONNENT en une seule force (N armées) ; les soutiens S d'alliés sur
     la case s'ajoutent à la force d'attaque correspondante
   - Force de défense : 1 par armée occupant la case + soutiens S alliés
     ciblant la case +1 chacun + CHÂTEAU +1 défensif fixe (si présent)
   - MULTI-ATTAQUANTS ENNEMIS sur la même case : les forces d'attaque
     s'affrontent entre elles ET contre la défense — la force la plus haute
     l'emporte
   - Force d'attaque > force de défense → VICTOIRE : les défenseurs sont
     battus (Phase 3), les attaquants gagnants occupent la case
   - Force d'attaque ≤ force de défense → STATU QUO : la défense tient,
     les attaquants restent sur place, leur A est un failure
   - Pas de coupe de soutien au MVP (raffinement futur, documente-le)
   - Égalité entre forces d'attaque ennemies : statu quo (personne ne
     bouge)
   - Le soutien S en LOOP : si AUCUNE attaque ne cible la case ce tour →
     SUCCÈS (la chaîne avance) ; si une attaque cible la case → soutien
     donné, index INCHANGÉ (reste en boucle)

4. Phase 3 — Retraites (GDD §6) :
   - Une pile battue se replie EN BLOC vers une case adjacente valide : non
     occupée par une armée, non ciblée par un combat ce tour, et différente
     de la case d'origine de l'attaquant (choix simple documenté : repli en
     bloc de la pile entière)
   - Deux piles (ou armées) se repliant sur la même case → les deux sont
     DÉTRUITES
   - Aucune case valide → la pile est DÉTRUITE
   - Si plusieurs cases valides : choix déterministe (première par ordre de
     ID de territoire — documente-le ; un choix joueur viendra plus tard)

5. Phase 4 — Progression des chaînes et contrôle territorial :
   - Par ordre exécuté, outcome ∈ { success, failure, invalid } :
     - success → CurrentIndex++ (chaîne consommée si dernier ordre ; l'armée
       devient Sans Ordre)
     - failure → single : chaîne BRISÉE (armée Sans Ordre) ; loop : index
       inchangé (retentative au tour suivant)
     - invalid → chaîne BRISÉE dans les deux modes
   - Boucle de veille (H/J en loop) : index figé, jamais d'échec
   - Boucle "coincée" (position devenue inaccessible) : retente indéfiniment
     — comportement attendu, le joueur remplace la chaîne (documente-le)
   - CONTRÔLE TERRITORIAL (GDD §8) : toute case occupée en fin de résolution
     (arrivée, fusion, conquête) bascule sous le contrôle du propriétaire
     des armées qui l'occupent (TerritoryState.OwnerID). Rémanence : le
     contrôle persiste après le départ des armées, jusqu'au passage d'un
     ennemi

6. Tests (internal/engine/resolve_test.go, scénarios exhaustifs) :
   - Mouvement : case vide (succès + contrôle), case alliée (failure),
     position manquante (failure)
   - Combat : égalité = statu quo ; supériorité = victoire + retraite ;
     défenseur sans case valide = détruit ; collision de repli = les deux
     détruits ; soutien S décisif / gaspillé ; château +1 ; attaquants
     alliés fusionnés (N) ; multi-attaquants ennemis (conflit, égalité)
   - J : fusion avec allié présent / arrivé le même tour ; ennemi = failure
   - D : intégrale vs partielle (single avance, loop retente) ; destination
     attaquée ; chaîne suit l'armée d'origine sur la 1re destination ;
     création d'armées avec matricules
   - P : infrastructure détruite + bonus R ; sans infrastructure = invalid
     (brise dans les deux modes)
   - S loop : sortie quand plus d'attaque ; index figé pendant l'attaque
   - Progression : single/loop/invalid appliqués sur chaînes MIXTES ;
     veille H/J ; chaîne consommée ; boucle coincée
   - Contrôle : conquête, rémanence après départ
   - DÉTERMINISME : deux appels Resolve sur le même état → résultats
     identiques (état final + événements)
   - L'état retourné est cohérent (armées référencent des territoires
     existants, piles cohérentes avec les fusions)

Critères d'acceptation :
- make test passe ; make vet passe ; aucune dépendance tierce ajoutée
- Resolve est pure, déterministe, sans I/O
- Les événements produits sont suffisants pour construire un TurnReport
  (P1.7) sans accès à l'état interne
- Les phases sont identifiables pour insérer ravitaillement (P1.5) et
  propagation (P2) sans refactor majeur

Note : documente dans ta réponse finale les choix ouverts que tu as tranchés
(ordre des destinations dans un repli, pile détruite vs armées, compteur de
matricules...) pour mise à jour des specs (ne modifie pas les specs
toi-même). Ne commite pas : je m'en charge.
```
