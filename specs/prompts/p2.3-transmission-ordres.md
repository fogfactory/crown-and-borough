# Prompt P2.3 — Transmission différée des ordres (messagers)

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le moteur existe (P1.4/P1.5/P1.6 : résolution, ravitaillement, hiver ; P2.1 :
soutien automatique ; P2.2 : vision T-x par joueur), le cycle de jeu et l'API
dev (P1.7), le parser (P1.3 : réception instantanée au MVP).
Références : specs/gdd.md (§4 Ordres par Messager, §3 Vitesse des messagers —
coûts dans les assets d'équilibrage) et specs/architecture.md (§6 Réception
de la chaîne).

PÉRIMÈTRE : les chaînes ne sont PLUS reçues instantanément : un messager part
du NOBLE ÉMETTEUR vers le PREMIER TERRITOIRE de la feuille d'ordres ; le
temps de trajet est fixé À L'ÉMISSION. Toute armée du joueur qui passe par ce
territoire entre l'arrivée et l'hiver suivant remplace sa chaîne par celle-ci.
PAS d'interception. La vision T-x (P2.2) reste telle quelle. P3 (API réelle,
auth, persistance) HORS périmètre.

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. CHANGEMENT DE SÉMANTIQUE (remplace la réception instantanée de P1.3) :
   - Une chaîne soumise (P1.7 /api/orders) n'est PLUS assignée immédiatement :
     elle devient un MESSAGE (messager) en attente de voyage
   - Point de DÉPART : la position COURANTE du NOBLE ÉMETTEUR (le noble de
     l'en-tête de la feuille ; s'il est à cheval sur une pile, la case de
     cette pile). Noble PRISONNIER → soumission REFUSÉE (erreur explicite ;
     un noble n'est jamais détruit — GDD §6)
   - CIBLE : le PREMIER TERRITOIRE de la feuille (XXX de `XXX A YYY`, le
     territoire de `H XXX` ou `P XXX`) — pas une armée
   - L'émission consomme la capacité du noble (1 émission/tour) au moment de
     la soumission, comme avant
   - ARRIVÉE : calculée À L'ÉMISSION — travelTime fixe (point 2) : le
     messager arrive au tour émission + ceil(travelTime), quelle que soit
     l'évolution du monde

2. VOYAGE (internal/engine, dans le cycle de jeu P1.7) :
   - Modèle : GameState.PendingOrders []PendingOrder { ID, PlayerID,
     NobleCode, Chain, TargetTerritoryID, EmissionTurn int, ArrivalTurn int }
   - travelTime = plus court chemin (Dijkstra, départage ID croissant) entre
     la case du noble à l'émission et le territoire cible, coûts lus dans
     les assets d'équilibrage (balance.json, section travel : plaine/route
     0,5 | forêt/colline 1 | montagne/marécage 2 | relais : coût divisé par
     2) ; ArrivalTurn = EmissionTurn + ceil(travelTime)
   - Pas de position de messager à suivre : l'arrivée est une DATE, le
     messager n'existe que comme ordre en attente

3. RÉCEPTION (fenêtre d'arrivée) :
   - Entre l'ArrivalTurn et la FIN de l'HIVER suivant, la PREMIÈRE ARMÉE du
     joueur émetteur présente sur le territoire cible (départage : plus
     petit matricule) reçoit la chaîne — appliquée à TOUTE sa pile
     (P1.3) : la pile REMPLACE sa chaîne actuelle (la chaîne reçue
     s'exécute à partir du tour suivant)
   - AUCUNE armée requise à l'émission : une armée peut arriver sur le
     territoire après l'émission et recevoir l'ordre dans la fenêtre
   - Une chaîne qui ÉCHOUE la validation de réception (D ≠ taille de la
     pile, nobles chevauchant non tous assignés — P1.3) est PERDUE
     (OrderLostEvent avec raison)
   - À la fin de l'hiver, une chaîne jamais reçue est PERDUE (détruite)
   - Deux chaînes reçues par la même pile le même tour → la plus RÉCEMMENT
     émise gagne (départage : ordre d'émission)
   - Le messager ne poursuit PAS une armée : il cible un TERRITOIRE
   - HIVER : les messagers voyagent aussi pendant l'hiver (l'hiver compte
     dans le temps de trajet) et la réception y est possible (les armées
     n'y bougent pas)

4. PAS D'INTERCEPTION : les ordres ne peuvent pas être interceptés par
   l'ennemi (choix documenté : la transmission est insensible au contrôle
   des cases traversées — les messagers passent partout)

5. EVENTS : PendingOrderEvent (émission : noble, cible, arrivée prévue),
   OrderArrivalEvent (territoire, armée, chaîne reçue, remplacement),
   OrderLostEvent (chaîne perdue à la fin de l'hiver) — intégrés au
   TurnReport (P1.7, section orders) ; pas de formatage

6. IMPACT API DEV (P1.7) : POST /api/orders crée les PendingOrders (plus
   d'assignation directe) ; l'état (state.json) expose les ordres en attente
   (cible, arrivée prévue) pour le debug (dev)

7. TESTS (internal/engine/messenger_test.go) :
   - DÉLAIS : noble → territoire à 2 cases de plaine (coût 1,0) → arrivée au
     tour suivant ; l'armée exécute SON ANCIENNE chaîne pendant le voyage
     (progression vérifiée), la nouvelle chaîne s'exécute au tour d'après
   - ARRIVÉE FIXÉE À L'ÉMISSION : l'armée (et le noble) bougent pendant le
     voyage → l'arrivée a quand même lieu à la date calculée, sur le
     TERRITOIRE cible (le noble repart avec la prochaine émission)
   - Vitesses du terrain : forêt (1/tour) et montagne (2/tour) ralentissent
     ; relais de poste sur le chemin accélère (coût divisé par 2) ; route =
     plaine (0,5) ; coûts lus dans balance.json (modifier les assets change
     les délais sans recompiler)
    - RÉCEPTION : aucune armée sur le territoire à l'arrivée → la chaîne
      attend ; une armée y passe dans la fenêtre → reçue (chaîne appliquée
      à toute la pile), ancienne chaîne remplacée ; plusieurs armées → le
      plus petit matricule gagne ; chaîne invalide à la réception (D ≠
      taille de pile, nobles non couverts) → perdue ; aucune armée avant
      l'hiver → chaîne perdue (OrderLostEvent)
   - REMPLACEMENT : deux messagers arrivant le même tour sur le même
     territoire → la chaîne émise le plus récemment gagne
    - SOUMISSION : noble prisonnier → refus ; joueur sans noble libre →
      refus ; capacité noble inchangée (1 émission/tour)
   - PAS D'INTERCEPTION : chemin traversant des cases ennemies → l'ordre
     arrive et est reçu normalement (test dédié)
   - DÉTERMINISME : deux simulations identiques → mêmes arrivées, mêmes
     réceptions, mêmes pertes ; cohérence (ArrivalTurn ≥ EmissionTurn + 1,
     chaînes référencées existantes)

Critères d'acceptation :
- make test passe ; make vet passe ; aucune dépendance tierce ajoutée
- La réception instantanée de P1.3 est remplacée proprement (le code de
  réception du parser reste, le cycle de jeu appelle l'arrivée) ; le reste
  du moteur (combat, ravitaillement, hiver, vision P2.2) est inchangé
- Les messagers vivent dans GameState (sérialisables JSON, round-trip)
- Le TurnReport expose les événements de messagers

Note : documente dans ta réponse finale les choix ouverts que tu as tranchés
(arrivée fixée à l'émission, cible = territoire et non armée, première armée
du territoire dans la fenêtre jusqu'à l'hiver, chaîne perdue à l'hiver,
dernière émission gagnante, pas d'interception) pour mise à jour des specs
(ne modifie pas les specs toi-même). Ne commite pas : je m'en charge.
```
