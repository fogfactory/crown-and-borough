# Prompt P1.6 — Phase d'Hiver : ordres d'hiver, investissements, bilan des stocks

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le moteur de résolution existe (P1.4, internal/engine : phases 0-5 — phase 0
ravitaillement ajoutée en P1.5), les modèles sont en place (internal/models),

Références : specs/gdd.md (§2 Phase d'Hiver, §7 Infrastructures et Maillage

PÉRIMÈTRE : phase d'Hiver COMPLÈTE — parser des ordres d'hiver, investissements
(recrutement, construction, amélioration), paiement de proche en proche,
conservation des stocks (50 %), rapatriement vers la Capitale. AUCUN ordre de
mouvement, AUCUN combat, AUCUN ravitaillement en hiver. Transmission différée
(P2) HORS périmètre (vision T0).

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. FICHIER D'ÉQUILIBRAGE — assets/balance.json :
   - TOUTES les constantes du moteur (P1.4, P1.5, P1.6) y sont stockées,
     éditables sans toucher au code : base_production, supply_range,
     depot_range_bonus, pillage_bonus, et les coûts :
       costs: { castle: 10, mill: 3, army: 1, noble: 2, post_relay: 2,
                watchtower: 4, supply_depot: 3 }
   - SETUP INITIAL (utilisé par P1.7 à la création de partie, PAS par
     ResolveWinter) :
       starting_armies: 1, starting_resources: 10 (proposition — équilibrage,
       le joueur ajuste dans le fichier)
     Chaque joueur commence sur un lieu-dit DISTINCT avec un château
     construit AUTOMATIQUEMENT (sans coût : c'est le setup, pas un
     investissement — ce château est sa capitale par défaut), starting_armies
     armée(s) sur ce lieu-dit et starting_resources R dans son stock local
   - JSON simple avec commentaires de documentation (fichier éditable à la
     main) ; loader : étends le package de chargement d'assets existant avec
     LoadBalance(dir string) (Balance, error) (crash au démarrage si
     invalide, valeurs manquantes interdites — les coûts sont explicites)
   - Balance est passée en PARAMÈTRE de Resolve (P1.4/P1.5) et ResolveWinter
     (pas de constante en dur dans le code du moteur ; si tu dois toucher
     Resolve pour lui passer Balance, fais-le proprement en mettant à jour
     les signatures et les tests existants)

2. INTERFACE :
   - ResolveWinter(game *models.GameState, balance Balance, orders
     []WinterOrder) (Resolution, error) — fonction PURE, déterministe, sans
     I/O, SÉPARÉE de Resolve (tours d'action)
   - WinterOrder : union discriminée
       RecruitNoble{ TerritoryID } | RecruitArmy{ TerritoryID } |
       Build{ TerritoryID, InfraType }   (construire ; moulin existant sur la
       case → AMÉLIORE le moulin, pas un nouvel ordre séparé) |
       ElectCapital{ TerritoryID }       (désigner le château de la case
       comme capitale)
     Les ordres sont traités DANS L'ORDRE SAISI (priorité du joueur : quand
     les réserves sont insuffisantes, le premier de la liste passe, le
     second est rejeté)
   - PARSER (même package que P1.3) : format des ordres d'hiver
     (specs/architecture.md §6, une ligne = un ordre) :
       R N XXX — recruter un Noble sur XXX
       R A XXX — recruter une Armée sur XXX
       C M XXX — construire/améliorer un Moulin sur XXX
       C C XXX — construire un Château sur XXX
       C R XXX — construire un Relais de Poste sur XXX
       C T XXX — construire une Tour de Guet sur XXX
       C D XXX — construire un Dépôt de Vivres sur XXX
       E C XXX — désigner le château de XXX comme Capitale
       L N XXX — libérer le noble prisonnier XXX (XXX = code trigramme du
       noble ; requis : noble PRISONNIER appartenant au joueur — le noble
       réapparaît LIBRE à la capitale de son propriétaire ; coût : 0,
       choix documenté)
     XXX = code de territoire (4 lettres) ; ligne malformée / code inconnu →
     ERREUR DE PARSING de tout le lot (numéro de ligne, comme les chaînes) ;
     ordre bien formé mais impossible → REJET individuel (événement) ; pas
     de chaîne, pas de position, pas de liaison
   - EVENTS : WinterStockEvent (par lieu-dit : stock avant/après les étapes),
     RecruitEvent (code + nom du noble, matricule de l'armée),
     BuildEvent/UpgradeEvent (territoire, type, niveau), RejectedEvent
     (ordre d'origine + raison) — pas de formatage
   - ResolveWinter NE change NI la saison NI le numéro de tour : le cycle
     des saisons (hiver → printemps, turn++) est câblé en P1.7

3. TRÊVE HIVERNALE : aucune chaîne traitée (index inchangés, armées
   immobiles), aucun combat, AUCUN ravitaillement/famine en hiver (choix
   documenté : les armées vivent sur la terre ; seule la conservation 50 %
   draine l'année)

4. PAIEMENT DE PROCHE EN PROCHE (GDD §2) : le coût d'un investissement est
   prélevé sur les stocks des lieux-dits CONTRÔLÉS par le joueur, dans
   l'ordre : (1) le territoire CIBLÉ lui-même s'il stocke (lieu-dit ou case
   avec château), (2) le lieu-dit contrôlé le PLUS PROCHE (distance BFS
   croissante, départage trigramme du territoire croissant), (3) le suivant,
   et ainsi de suite. Chaque stock est épuisé (décrémenté à 0 si besoin)
   avant de passer au suivant. Si le TOTAL des réserves du joueur < coût →
   ordre REJETÉ (aucun prélèvement partiel, rien n'est prélevé)
   (réserves = somme des stocks de ses lieux-dits contrôlés, châteaux
   compris)

5. RECRUTEMENT :
   - Noble (coût noble) : crée UN Noble sur le territoire CIBLÉ (requis :
     contrôlé par le joueur ET contenant AU MOINS UNE armée du joueur — un
     noble ne peut pas être seul, GDD §6) ; nom = "Prénom de <Nom du
     territoire>" (ex. "Jacques de Notombes") ; le prénom est TIRÉ
     DÉTERMINISTIQUEMENT de prenoms.csv (RNG seedé par la seed de la partie
     + tour — le tirage est donc reproductible, "hasard" ne signifie pas
     non-déterminisme) ; code = trigramme du prénom tiré ; si ce code est
     déjà porté par un noble de la partie → prénom SUIVANT dans l'ordre du
     fichier (déterministe)
   - Armée (coût armée) : crée UNE armée (matricule suivant, compteur
     incrémenté) sur le territoire CIBLÉ (requis : contrôlé par le joueur)
   - L N XXX (libération, coût 0) : le noble prisonnier XXX du joueur
     réapparaît LIBRE à la case de la CAPITALE de son propriétaire
     (LocationID = capitale ; status free) ; noble non prisonnier ou
     appartenant à un autre joueur → REJET ; le noble est libéré même si la
     capitale n'a pas d'armée (cas limite toléré, GDD §6)

6. CONSTRUCTION (Build) :
   - Exigence de contrôle : case contrôlée par le joueur, sinon REJET
   - STRUCTURE UNIQUE : une seule infrastructure par case — construction sur
     une case déjà pourvue d'une infrastructure → REJET ; C M sur un moulin
     existant = AMÉLIORATION (niveau +1, coût moulin) ; C M sur toute autre
     infrastructure → REJET
   - Moulin : la case doit être un lieu-dit OU directement adjacente à un
     lieu-dit (règle des orphelins GDD §7), sinon REJET
   - Château : n'importe quelle case contrôlée — REND LA CASE LIEU-DIT
     (production + stockage dès le printemps suivant ; la phase 0 de P1.5
     le prend déjà en compte)
   - Relais / Tour / Dépôt : n'importe quelle case contrôlée
   - Effets déjà actifs : moulin +1 R/niveau (P1.5), dépôt +2 portée (P1.5),
     château +1 défense (P1.4) ; tour (vision T0) et relais (vitesse
     messagers) : effets en P2

6b. CAPITALE (GDD §2) :
   - MODÈLE : la capitale n'est PAS un territoire : ajoute au modèle Player
     un champ CapitalCastleID (InfraID, nullable — la désignation d'un
     joueur : le château qu'il considère comme sa capitale) ; le concept
     "Capitale = lieu-dit" de P1.1 est ABANDONNÉ (mets le modèle à jour et
     corrige les tests modèles concernés)
   - Défaut : la capitale d'un joueur est son PREMIER château — toute
     construction de château par un joueur SANS capitale le désigne
     automatiquement comme sa capitale
   - E C XXX : désigne le château de XXX comme capitale (remplace la
     désignation actuelle) ; requis : un château du joueur sur XXX ET le
     contrôle de la case (la capitale ne peut jamais être ennemie), sinon
     REJET
   - Si le château désigné est DÉTRUIT (pillage) : la désignation est
     perdue ; le prochain château construit redevient capitale par défaut
   - Rapatriement (étape 7) : destination = la case de la capitale du
     joueur ; si le joueur ne contrôle AUCUN château → PAS de rapatriement
     (les stocks restent en place après conservation)

7. CONSERVATION (Règle des 50 %) puis RAPATRIEMENT :
   - Ordre de la phase : (1) investissements, (2) CONSERVATION, (3)
     RAPATRIEMENT (la conservation précède le rapatriement pour que les
     plafonds du rapatriement aient du sens — choix documenté)
   - Conservation : sur CHAQUE lieu-dit (contrôlé ou non) : stock =
     ceil(stock / 2)
   - Rapatriement : chaque lieu-dit (hors château) garde au maximum 1 R,
     chaque case-château (hors capitale) garde au maximum 2 R, TOUT le
     surplus est transféré au stock de la case de la CAPITALE du joueur
     (contrôleur du lieu-dit) ; la capitale ACCUMULE (pas de plafond pour
     elle) ; une case sans lieu-dit n'a jamais de stock (rien à rapatrier) ;
     si le joueur ne contrôle AUCUN château → PAS de rapatriement (les
     stocks restent en place)

8. TESTS (internal/engine/winter_test.go, scénarios exhaustifs) :
   - Parser : les 7 formes valides ; ligne malformée → erreur de parsing du
     lot (numéro de ligne) ; code de territoire inconnu → erreur ; casse
     insensible
   - Paiement de proche en proche : cible-lieu-dit payée D'ABORD ; puis le
     lieu-dit contrôlé le plus proche (distance BFS) ; départage trigramme ;

   - Recrutement Noble : noble créé sur la cible, nom "Prénom de Territoire",
     code unique (deux recrutements → deux prénoms distincts), tirage
     déterministe (même seed → même prénom), cible non contrôlée → REJET ;
     cible SANS armée du joueur → REJET (un noble ne peut pas être seul)
   - LIBÉRATION : L N d'un noble prisonnier → libre à la capitale de son
     propriétaire ; noble non prisonnier → REJET ; noble d'un autre joueur
     → REJET ; coût 0
   - Recrutement Armée : armée créée sur la cible, matricule suivant ;
     cible non contrôlée → REJET
   - Construction : contrôle requis ; structure unique (rejet sur case

     lieu-dit non adjacent → REJET ; château en zone sauvage → la case
     devient une source pour P1.5 (test croisé : armée nourrie à portée au
     printemps suivant)
   - Ordre de phase : stock 10 + investissement 6 → reste 4 → conservation
     → 2 → rapatriement : lieu-dit garde 1, 1 va à la Capitale (prouve
     investir → conserver → rapatrier) ; château stock 5 → conserve 3 →
     garde 2, 1 vers la Capitale ; lieu-dit neutre : conservé (50 %) et
     rapatrié vers la Capitale de son contrôleur
   - CAPITALE : premier château construit = capitale par défaut (le joueur
     sans capitale qui construit un château le devient) ; E C XXX :
     re-désignation (château + contrôle requis, sinon REJET) ; capitale

     SANS aucun château contrôlé → PAS de rapatriement (stocks en place) ;
     la capitale accumule (pas de plafond), les autres châteaux gardent ≤ 2,
     les lieux-dits ≤ 1
   - Trêve : chaînes inchangées (index identiques), armées immobiles,
     aucune famine (pile de 10 en hiver : aucun coût)
   - balance.json : chargement, valeur par défaut absente → crash explicite ;

   - DÉTERMINISME : deux appels ResolveWinter sur le même état + mêmes
     ordres + même balance → résultats identiques (état final + événements) ;
     cohérence de l'état (stocks ≥ 0, IDs uniques, matricules croissants)
```
