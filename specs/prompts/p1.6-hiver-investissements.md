# Prompt P1.6 — Phase d'Hiver : ordres d'hiver, investissements, bilan des stocks

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le moteur de résolution existe (P1.4, internal/engine : phases 0-5 — phase 0

PÉRIMÈTRE : phase d'Hiver COMPLÈTE — parser des ordres d'hiver, investissements

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. FICHIER D'ÉQUILIBRAGE — assets/balance.json :
   - TOUTES les constantes du moteur (P1.4, P1.5, P1.6, et les coûts de
      trajet de P2.2/P2.3) y sont stockées, éditables sans toucher au code :
       base_production, supply_range, depot_range_bonus, pillage_bonus, et
       les coûts :
         costs: { castle: 10, mill: 3, troop: 1, noble: 2, post_relay: 2,
                  watchtower: 4, supply_depot: 3, liberation: 0 }
      et la section travel (utilisée par P2.2/P2.3 — structure à définir,
      proposée : coût par terrain plaine/route 0,5, forêt/colline 1,

    - SETUP INITIAL (utilisé par P1.7 à la création de partie, PAS par
      ResolveWinter) :
        starting_nobles: 1, starting_troops: 1, starting_resources: 10
        (proposition — équilibrage, le joueur ajuste dans le fichier)
      Chaque joueur commence sur un village DISTINCT avec un château
      construit AUTOMATIQUEMENT (sans coût : c'est le setup, pas un
      investissement — ce château est sa capitale par défaut), starting_nobles
      noble(s), starting_troops troupe(s) sur cette case productive et
      starting_resources R dans son stock local
   - JSON simple avec commentaires de documentation (fichier éditable à la

   - Balance est passée en PARAMÈTRE de Resolve (P1.4/P1.5) et ResolveWinter

2. INTERFACE :

     map[PlayerID][]WinterOrder) (Resolution, error) — fonction PURE,
     déterministe, sans I/O, SÉPARÉE de Resolve (tours d'action). Les ordres
     de CHAQUE joueur sont traités dans l'ordre saisi, les joueurs par ID

     globalement (étape 7)
   - WinterOrder : union discriminée
        RecruitNoble{ TerritoryID } | RecruitTroop{ TerritoryID } |
        Build{ TerritoryID, InfraType }   (construire ; moulin existant sur la
        case → AMÉLIORE le moulin, pas un nouvel ordre séparé) |
        ElectCapital{ TerritoryID }       (désigner le château de la case
        comme capitale) |
        LiberateNoble{ NobleCode }        (libérer un noble prisonnier)
     Les ordres sont traités DANS L'ORDRE SAISI (priorité du joueur : quand
     les réserves sont insuffisantes, le premier de la liste passe, le
     second est rejeté)
   - PARSER (même package que P1.3) : format des ordres d'hiver
     (specs/architecture.md §6, une ligne = un ordre) :
R N XXX — recruter un Noble sur XXX
        R T XXX — recruter une Troupe sur XXX
       C M XXX — construire/améliorer un Moulin sur XXX
       C C XXX — construire un Château sur XXX
       C R XXX — construire un Relais de Poste sur XXX
       C T XXX — construire une Tour de Guet sur XXX
       C D XXX — construire un Dépôt de Vivres sur XXX
       E C XXX — désigner le château de XXX comme Capitale
        L N XXX — libérer le noble prisonnier XXX (XXX = code trigramme du
        noble ; requis : noble PRISONNIER appartenant au joueur ET une
        CAPITALE désignée — sans capitale, REJET — le noble réapparaît
        LIBRE à la capitale de son propriétaire ; coût : balance.json,
        défaut 0)
      XXX = code de territoire (trigramme de 3 lettres pour tout territoire) ; ligne
     malformée / code inconnu →
     ERREUR DE PARSING de tout le lot (numéro de ligne, comme les chaînes) ;
     ordre bien formé mais impossible → REJET individuel (événement) ; pas

- EVENTS : WinterStockEvent (par case productive : stock avant/après les
   étapes),
      RecruitEvent (code + nom du noble, matricule de la troupe),

3. TRÊVE HIVERNALE : aucune chaîne traitée (index inchangés, troupes
   immobiles), aucun combat, AUCUN ravitaillement/famine en hiver (choix
   documenté : les troupes vivent sur la terre ; seule la conservation 50 %
   draine l'année)

4. PAIEMENT DE PROCHE EN PROCHE (GDD §2) : le coût d'un investissement est
   prélevé sur les stocks des lieux-dits CONTRÔLÉS par le joueur, dans
   l'ordre : (1) le territoire CIBLÉ lui-même s'il stocke (village ou case
   avec château), (2) le château ou village contrôlé le PLUS PROCHE (distance
   BFS
   croissante, départage trigramme du territoire croissant), (3) le suivant,
   et ainsi de suite. Chaque stock est épuisé (décrémenté à 0 si besoin)
   avant de passer au suivant. Si le TOTAL des réserves du joueur < coût →
   ordre REJETÉ (aucun prélèvement partiel, rien n'est prélevé)
   (réserves = somme des stocks de ses lieux-dits contrôlés, châteaux
   compris)

5. RECRUTEMENT :
   - Noble (coût noble) : crée UN Noble sur le territoire CIBLÉ (requis :
     contrôlé par le joueur ET contenant AU MOINS UNE troupe du joueur — un
     noble ne peut pas être seul, GDD §6) ; nom = "Prénom de <Nom du
     territoire>" (ex. "Jacques de Notombes") ; le prénom est TIRÉ
     DÉTERMINISTIQUEMENT de prenoms.csv (RNG seedé par la seed de la partie
     + tour — le tirage est donc reproductible, "hasard" ne signifie pas
     non-déterminisme) ; code = trigramme du prénom tiré ; si ce code est
     déjà porté par un noble de la partie → prénom SUIVANT dans l'ordre du
     fichier (déterministe)
   - Troupe (coût troupe) : crée UNE troupe (matricule suivant, compteur
     incrémenté) sur le territoire CIBLÉ (requis : contrôlé par le joueur)
    - L N XXX (libération, coût balance — défaut 0) : le noble prisonnier
      XXX du joueur réapparaît LIBRE à la case de la CAPITALE de son
      propriétaire (LocationID = capitale ; status free) ; noble non
      prisonnier ou appartenant à un autre joueur → REJET ; AUCUNE capitale
      désignée → REJET ; le noble est libéré même si la capitale n'a pas
      de troupe (cas limite toléré, GDD §6)

6. CONSTRUCTION (Build) :
   - Exigence de contrôle : case contrôlée par le joueur, sinon REJET
   - STRUCTURE UNIQUE : une seule infrastructure par case — construction sur
     une case déjà pourvue d'une infrastructure → REJET ; C M sur un moulin
     existant = AMÉLIORATION (niveau +1, coût moulin) ; C M sur toute autre
     infrastructure → REJET
   - Moulin : la case doit être productive (village) OU un château y est
     présent OU directement adjacente à une case productive
     (règle des orphelins GDD §7), sinon REJET
   - Château : n'importe quelle case contrôlée — REND LA CASE PRODUCTIVE (et
     remplace un éventuel village)
     (production + stockage dès le printemps suivant ; la phase 0 de P1.5
     le prend déjà en compte)
   - Relais / Tour / Dépôt : n'importe quelle case contrôlée
   - Effets déjà actifs : moulin +1 R/niveau (P1.5), dépôt +2 portée (P1.5),
     château +1 défense (P1.4) ; tour (vision T0) et relais (vitesse
     messagers) : effets en P2

6b. CAPITALE (GDD §2) :
   - MODÈLE : la capitale n'est PAS un territoire : ajoute au modèle Player
     un champ CapitalCastleID (InfraID, nullable — la désignation d'un
     joueur : le château qu'il considère comme sa capitale) ; le concept
"Capitale = village/château" de P1.1 est ABANDONNÉ (mets le modèle à
      jour et corrige les tests modèles concernés)
   - Défaut : la capitale d'un joueur est son PREMIER château — toute
     construction de château par un joueur SANS capitale le désigne
     automatiquement comme sa capitale
   - E C XXX : désigne le château de XXX comme capitale (remplace la
     désignation actuelle) ; requis : un château du joueur sur XXX ET le
     contrôle de la case (la capitale ne peut jamais être ennemie), sinon
     REJET
    - Si le château désigné est DÉTRUIT (pillage) : la désignation est
      perdue et le joueur n'a PLUS de capitale — PAS de capitale intérimaire
      (pas de rapatriement entre-temps, L N rejeté) — jusqu'à ce qu'un
      nouvel E C ou un nouveau château construit (capitale par défaut) la
      redésigne
    - Rapatriement (étape 7) : destination = la case de la capitale du
      joueur ; si le joueur n'a AUCUNE capitale désignée (aucun château
      contrôlé, ou désignation perdue et non redésignée) → PAS de
      rapatriement (les stocks restent en place après conservation)

7. CONSERVATION (Règle des 50 %) puis RAPATRIEMENT :
   - Ordre de la phase : (1) investissements, (2) CONSERVATION, (3)
     RAPATRIEMENT (la conservation précède le rapatriement pour que les
     plafonds du rapatriement aient du sens — choix documenté)
- Conservation : sur CHAQUE case à stock (village ou château, contrôlé ou
      non) : stock = ceil(stock / 2)
     - Rapatriement : chaque case productive SANS château (village) garde au
      maximum 1 R, chaque case-château (hors capitale) garde au maximum 2 R,
      TOUT le surplus est transféré au stock de la case de la CAPITALE du
      joueur (contrôleur de la case) ; la capitale ACCUMULE (pas de plafond
      pour elle) ; une case non productive n'a jamais de stock (rien à
      rapatrier) ;
      un village NON contrôlé est conservé (50 %) mais PAS rapatrié (pas
      de contrôleur) ; si le joueur n'a AUCUNE capitale désignée → PAS de
      rapatriement (les stocks restent en place)
```
