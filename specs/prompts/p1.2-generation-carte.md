# Prompt P1.2 — Génération de carte Voronoï

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le squelette Go existe (cmd/server, internal/{api,engine,db,models}), les
modèles métier sont définis dans internal/models (Territory, GameState, enums),
les assets CSV sont chargés par un loader existant (Assets avec Communes,
Prenoms, Qualificatifs). Le front React (web/) affiche déjà un MapViewer
générique (props map + state) sur fixtures.
Références : specs/gdd.md (section 3), specs/roadmap.md (P1.2 détaillé),
specs/architecture.md (contrat map.json).

Tâche : implémenter la génération de carte dans internal/engine/mapgen et
l'exposer via un endpoint dev.

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu (noms de communes,
qualificatifs) sont en français.

1. Package internal/engine/mapgen :
   - Entrée : func Generate(seed string, assets assetgen.Assets, cfg Config) (MapData, error)
     où Config { Width, Height int (ex. 1000x700), SiteCount int (ex. 64),
     LieuDitRatio float64 (0.25) }
   - MapData : struct JSON-exportable conforme au contrat map.json
     (territories: [{ id, code, name, terrain, lieuDit, points: [[x,y],...],
     adjacencies: [id,...] }]) — la géométrie vit ICI, pas dans internal/models.
   - Déterminisme : même seed → carte identique (byte-for-byte sur la sortie
     JSON). Pure fonction de (seed, assets, cfg), sans état global ni
     horloge/aléa non seedé.

2. Algorithme (liberté d'implémentation, contraintes suivantes) :
   - Cellules Voronoï depuis des sites générés de façon seedée avec
     jitter/irrégularité → territoires de tailles INÉGALES (une grille
     purement régulière est interdite).
   - Méthode conseillée si pas de lib : grille fine (ex. 256x160) assignée
     au site le plus proche (distance euclidienne) + extraction des polygones
     et de leurs frontières. Une lib de voronoï est tolérée si justifiée,
     sinon stdlib uniquement.
   - Graphe d'adjacence géométrique : deux cellules adjacentes si elles
     partagent une frontière significative (longueur ≥ seuil, à définir).
   - Frontières infranchissables : les paires de terrains montagne/montagne
     et montagne/marécage sont infranchissables avec forte probabilité (≥ 70 %),
     les paires plaine/plaine toujours franchissables ; le reste probabilité
     faible (≤ 20 %). Seedé.
   - Routes : après suppression des frontières, si le graphe est déconnecté
     ou contient une feuille (degré 1), ajoute des routes (arêtes) entre des
     territoires NON adjacents géométriquement (choix seedé : relier deux
     composantes / donner un second voisin à une feuille, de préférence vers
     le plus proche). Les routes ne sont PAS des adjacences géométriques :
     ce sont de simples arêtes du graphe final.
   - INVARIANT ABSOLU : le graphe final (adjacences franchissables + routes)
     est CONNEXE et SANS CUL-DE-SAC SUR AUCUNE CELLULE, BORDS COMPRIS
     (degré ≥ 2 partout, y compris les cellules de bord qui forment un anneau).
     Toute feuille résiduelle est corrigée par ajout de route.

3. Terrains et lieux-dits :
   - Attribution des terrains (plain | forest | hill | mountain | swamp) :
     distribution seedée avec préférence pour des zones contiguës
     (méthode simple acceptée : bruit de faible fréquence ou smoothing
     local ; à défaut tirage pondéré). Chaque terrain doit être présent.
   - Lieux-dits : ~25 % des territoires (cf. LieuDitRatio), choix seedé ;
     leur terrain reste leur terrain (lieux-dits sur tout relief).
   - Production R de base d'un lieu-dit : hors scope (moteur P1.5) — la
     génération fournit seulement le flag lieuDit.

4. Nommage (à partir des assets) :
   - LIEU-DIT : nom = commune de communes.csv, code = trigramme (3 lettres).
   - NON LIEU-DIT : qualificatif de qualificatifs.csv selon le terrain
     dominant (terrain == "any" réservé au qualificatif "Marches" pour les
     territoires de bordure, sinon ignoré) + nom d'une commune d'un lieu-dit
     ADJACENT (fallback : lieu-dit le plus proche par distance de centroïde).
     Nom = "{Qualificatif} de {Commune}" (ex. "Forêt de Rosemont"), code =
     "{prefix}{trigramme}" (ex. FROS, 4 lettres).
    - Contraintes : codes uniques sur toute la carte ; combinaison
      qualificatif+commune unique (un même couple ne nomme pas deux
      territoires) — en cas de collision : qualificatif suivant compatible
      avec le terrain, puis commune la plus proche suivante (déterministe,
      seedé) ; au moins une commune utilisée par la carte ; tous les codes
      en MAJUSCULES A-Z.
   - Chaque commune de communes.csv peut nommer au plus UN lieu-dit (les
     communes inutilisées restent disponibles pour la suite).

5. Endpoint dev /api/map (handler dans internal/api, enregistré dans
   cmd/server) :
   - GET /api/map → MapData en JSON (générée avec un seed de DEV : variable
     d'environnement SEED ou valeur par défaut constante, loguée au démarrage)
   - CORS autorisé pour http://localhost:5173 (dev front) — middleware
     minimal, pas de dépendance ajoutée
   - /healthz inchangé ; make run doit suffire à tester localement

6. Front (web/) : brancher la vraie carte
   - Ajouter un proxy Vite : /api → http://localhost:8080 (vite.config.ts)
   - App.tsx : charger GET /api/map et l'afficher dans MapViewer (remplacer
     la fixture map ; la couche dynamique state reste vide/minimale pour
     l'instant — elle sera branchée en P1.7)
   - La fixture map.ts peut être supprimée ; state.ts conservé en attendant
     P1.7 (ou vide si trop incohérent avec la vraie carte : à toi de juger,
     mais le MapViewer doit rendre une carte sans couche dynamique sans bug)
   - Nouveau champ README d'usage : (1) make run (backend), (2) make web-dev
     (front), (3) ouvrir http://localhost:5173

7. Tests (internal/engine/mapgen/mapgen_test.go) :
   - Déterminisme : generate(seed, assets) → identique à l'octet sur deux
     appels ; deux seeds différents → cartes différentes
   - Graphe : connexité (BFS depuis n'importe quel territoire atteint tout),
     degré ≥ 2 sur TOUTES les cellules (bords compris), adjacences symétriques
   - Lieux-dits : ratio ∈ [0.20, 0.30] sur plusieurs seeds
   - Codes : format (3 lettres lieux-dits, 4 lettres sinon, MAJUSCULES A-Z),
     unicité globale sur plusieurs seeds
   - Nommage : tout territoire a un nom non vide ; non-lieu-dit suit le motif
     "{Qualificatif} de {Commune}" ; chaque terrain présent sur la carte
   - Géométrie : polygones non vides, dans les bornes du viewport, frontières
     extraites cohérentes (pas de trou de grille)

Critères d'acceptation :
- make test passe (tous les tests, y compris modèles inchangés)
- make vet passe
- make run + GET /api/map renvoie un JSON valide conforme au contrat
- make web-dev : la carte réelle s'affiche dans le navigateur (zoom, sélection,
  légende OK), sans erreur console
- Aucune régression front : npm run build && npm run lint dans web/

Note : si tu dois faire évoluer internal/models (ex. structures d'adjacence),
documente précisément le changement dans ta réponse finale pour mise à jour
des specs. Ne modifie pas les specs toi-même. Ne commite pas : je m'en charge.
```
