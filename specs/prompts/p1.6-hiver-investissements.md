# Prompt P1.6 — Phase d'Hiver : conservation des stocks, recrutement et construction

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le moteur de résolution existe (P1.4, internal/engine : phases 0-5 — phase 0
ravitaillement ajoutée en P1.5), les modèles sont en place (internal/models),
la génération de carte aussi (internal/engine/mapgen).
Références : specs/gdd.md (§2 Phase d'Hiver, §7 Infrastructures et Maillage
Productif) et specs/architecture.md.

PÉRIMÈTRE : résolution de la phase d'Hiver : trêve, investissements
(recrutement de Nobles, construction/upgrade d'Infrastructures), conservation
des stocks (règle des 50 %). AUCUN ordre, AUCUN combat, AUCUN ravitaillement
en hiver. La transmission différée (P2) est HORS périmètre (vision T0).

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. INTERFACE (internal/engine) :
   - ResolveWinter(game *models.GameState, investments []Investment)
     (Resolution, error) — fonction PURE, déterministe, sans I/O, SÉPARÉE
     de Resolve (les tours d'action)
   - Investment : union discriminée
       Recruit                                        (recruter un Noble)
       Build{ TerritoryID, InfraType, }               (construire)
       Upgrade{ TerritoryID, }                        (améliorer le moulin)
     L'ordre des investissements dans la liste est l'ordre de priorité du
     joueur : ils sont traités DANS L'ORDRE SAISI (choix documenté : l'ordre
     compte quand la trésorerie est insuffisante, c'est une décision
     stratégique du joueur)
   - EVENTS ajoutés à Resolution : WinterEvent (par lieu-dit : stock avant,
     après, montant de la perte 50 %), RecruitEvent (code noble, matricule
     d'armée), BuildEvent (territoire, type, niveau), UpgradeEvent,
     RejectedInvestmentEvent (investissement + raison) — pas de formatage
   - Constants moteur : RecruitCost (int, défaut 5), BuildCost (int, défaut
     5) — documentées
   - ResolveWinter NE change NI la saison NI le numéro de tour : le cycle
     des saisons (hiver → printemps, turn++) est câblé en P1.7

2. TRÊVE HIVERNALE : aucune chaîne n'est traitée (index inchangés, armées
   immobiles), aucun combat, AUCUN ravitaillement/famine (choix documenté :
   les armées vivent sur la terre en hiver — la perte hivernale des stocks
   est le seul drain de l'année)

3. TRÉSORERIE ET PAIEMENT : les réserves du joueur = somme des stocks
   (TerritoryState.Resources) de ses lieux-dits CONTRÔLÉS
   (OwnerID == joueur) — y compris les cases rendues lieu-dit par un château.
   Chaque investissement est payé en prélevant les stocks dans un ordre
   DÉTERMINISTE : du plus PETIT stock au plus GRAND, départage trigramme du
   territoire croissant (même convention que le balayage famine de P1.5).
   Si le total des réserves < coût → investissement REJETÉ (pas de paiement
   partiel, rien n'est prélevé, événement RejectedInvestmentEvent)

4. RECRUTEMENT (Recruit, coût RecruitCost) : crée UN Noble au capital du
   joueur (Noble.LocationID = Capitale) ACCOMPAGNÉ d'UNE armée (nouveau
   matricule, Army.TerritoryID = Capitale — choix documenté : recruter un
   noble = recruter ses hommes ; si tu préfères noble seul, note-le dans ta
   réponse). Le code du noble = premier trigramme de prenoms.csv non encore
   utilisé par un noble de la partie (ordre du fichier, déterministe).
   Si la Capitale n'est PAS contrôlée par le joueur → recrutement REJETÉ

5. CONSTRUCTION (Build, coût BuildCost par opération ; Upgrade du moulin :
   coût BuildCost aussi) :
   - Exigence de contrôle : la case doit être contrôlée par le joueur
     (TerritoryState.OwnerID == joueur), sinon REJET
   - STRUCTURE UNIQUE (GDD §7) : une seule infrastructure par case — toute
     construction sur une case portant déjà une infrastructure est REJETÉE ;
     l'Upgrade est autorisé sur un MOULIN existant (mill, niveau +1) et lui
     seul (upgrader un autre type → REJET)
   - Moulin (mill) : la case doit être un lieu-dit OU directement adjacente
     à un lieu-dit (règle des orphelins GDD §7), sinon REJET
   - Château (castle) : n'importe où (contrôlé) — REND LA CASE LIEU-DIT
     (production + stockage dès le printemps suivant) ; la phase 0 de P1.5
     doit le prendre en compte (déjà documenté dans le prompt P1.5 : case
     avec château = source)
   - Relais de Poste (post_relay), Tour de Guet (watchtower), Dépôt de
     Vivres (supply_depot) : n'importe quelle case contrôlée
   - Effets : le moulin augmente la production (+1 R/niveau, phase 0 de
     P1.5), le dépôt étend la portée (+2, P1.5), la tour donne la vision T0
     (P2), le relais double la vitesse des messagers (P2), le château donne
     +1 en défense (déjà actif dans les combats de P1.4)

6. CONSERVATION (Règle des 50 %, GDD §2) : APRÈS tous les investissements,
   sur CHAQUE lieu-dit (contrôlé ou non — les stocks des lieux-dits neutres
   sont aussi conservés) : stock = ceil(stock / 2). Les cases sans lieu-dit
   n'ont jamais de stock. ORDRE IMPÉRATIF : investir d'abord, conserver
   ensuite (le texte du GDD : "après investissement")

7. TESTS (internal/engine/winter_test.go, scénarios exhaustifs) :
   - Conservation : 10 → 5 ; 3 → 2 (ceil) ; 1 → 1 ; 0 → 0 ; lieu-dit neutre
     aussi conservé ; case non lieu-dit : stock toujours 0
   - ORDRE : stock 10, investissement 6 → reste 4 → conservé à 2 (prouve
     qu'on investit AVANT de conserver)
   - Paiement plus petit stock d'abord : stocks {A:2, B:8}, invest 5 →
     A:0, B:5 → puis conservation : A:0, B:3
   - Réserves insuffisantes : total 4, invest 5 → REJETÉ, stocks intacts
   - Ordre de priorité : deux investissements dont le total > réserves →
     le premier de la liste passe, le second est rejeté
   - Recrutement : noble créé au capital + armée (matricule suivant,
     compteur incrémenté), code = premier trigramme libre de prenoms.csv ;
     deuxième recrutement → code suivant ; capital perdu → rejeté
   - Construction : sur case contrôlée = OK ; case non contrôlée = rejet ;
     case avec infrastructure = rejet (structure unique) ; moulin hors
     lieu-dit non adjacent = rejet ; moulin sur lieu-dit ou adjacent = OK ;
     château en zone sauvage → la case devient une source pour P1.5 (test
     croisé : armée nourrie à portée d'une case-château au tour suivant) ;
     upgrade moulin = niveau +1, re-coût BuildCost ; upgrade d'un relais =
     rejet
   - Trêve : chaînes inchangées (index identiques), armées immobiles,
     aucune famine (pile de 10 en hiver : aucun coût, aucun événement de
     famine)
   - DÉTERMINISME : deux appels ResolveWinter sur le même état et les mêmes
     investissements → résultats identiques (état final + événements) ;
     cohérence de l'état (stocks ≥ 0, IDs uniques)

Critères d'acceptation :
- make test passe ; make vet passe ; aucune dépendance tierce ajoutée
- ResolveWinter est isolée (aucun impact sur Resolve des tours d'action) et
  pure ; les événements suffisent à construire le bilan d'hiver du
  TurnReport (P1.7) sans accès à l'état interne
- Le cycle de saisons reste à brancher en P1.7 sans refactor

Note : documente dans ta réponse finale les choix ouverts que tu as tranchés
(noble + armée au recrutement, coûts RecruitCost/BuildCost, pas de
ravitaillement en hiver, paiement plus petit stock d'abord, traitement dans
l'ordre saisi, allocation automatique du code noble, capital requis, rejet
sans paiement partiel) pour mise à jour des specs (ne modifie pas les specs
toi-même). Ne commite pas : je m'en charge.
```
