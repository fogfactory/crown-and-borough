# Plan P1.2f — État d'exemple (demo state) au front

Brief d'exécution autonome pour un modèle d'implémentation.

## Contexte

P1.2a→P1.2e sont faits : vocabulaire troupe/armée, villages, nommage communes, géométrie/graphe
v2, règles vivrières documentées. La génération de carte existe (`internal/engine/mapgen`,
`GET /api/map?players=N`), les modèles aussi (`internal/models`, `GameState` SANS `asOf`,
réservé à P2), le front (`MapViewer`) consomme un STUB d'état (`web/src/fixtures/state.ts`)
qui laisse la couche vivante vide. Le prompt source est
`specs/prompts/p1.2f-etat-exemple.md` — le lire en entier avant de commencer.

NATURE DE LA TÂCHE : code + branchement front + docs. Générer un ÉTAT D'EXEMPLE
(demo game state) déterministe sur la vraie carte générée, le servir via un endpoint dev
`GET /api/state` (DTO `StateView` explicite, PAS le marshaling direct du `GameState`), et
brancher le front dessus pour vérifier manuellement la couche vivante. Remplacer le stub
`web/src/fixtures/state.ts`.

Contraintes absolues :

- Code EXCLUSIVEMENT en anglais ; contenu de jeu en français.
- Déterminisme : même seed → même état byte-for-byte (mêmes octets JSON).
- `GameState` reste SANS `asOf` (champ réservé à P2) ; la fraîcheur vit dans le DTO.
- Ne rien commiter. Fichiers modifiés : ceux listés dans les étapes 1-5 ci-dessous.
- Docs modifiés UNIQUEMENT (dérogation P1.2a étendue) : `specs/architecture.md`,
  `specs/roadmap.md`, `specs/prompts/p1.7-rapport-tour-hotseat.md` (+ ce plan).
  Tous les autres fichiers de specs : LAISSÉS TELS QUELS.

## Difficulté et modèle recommandé

Difficulté **3/5**. Tâche moyenne, très bien spécifiée, sans zone d'ombre bloquante. Le
cœur est l'étape 1 (`internal/engine/demo`) : faisceau de contraintes déterministes à
respecter simultanément (déduction de trigrammes, villages laissés neutres, double
indexation `TerritoryStates` exigée par `Validate`, unicité des IDs). Risque principal :
l'oubli silencieux d'une contrainte — rattrapé par les tests déjà listés dans le prompt.
Un modèle de milieu de gamme suffit avec ce plan ; un modèle haut de gamme apporte une
assurance supplémentaire uniquement sur l'étape 1. Le refactor du cache dans `cmd/server`
(étape 3) a un risque faible de casser `TestMapResolverCachesStableBytes` : vérifier ce
test après modification.

## Décisions de conception (à appliquer et documenter dans la réponse finale)

1. **RNG déterministe dans `demo`** : `mapgen.newRNG` (sha256 + PCG, `math/rand/v2`) est
   non exporté → DUPLIQUER le helper (~15 lignes) dans `internal/engine/demo` avec un
   commentaire renvoyant à mapgen, plutôt que de modifier l'API de mapgen. Phases
   dérivées du seed : `"players"`, `"starts"`, `"control"`, `"nobles"`, `"infras"`,
   `"freshness"`. Même seed que `/api/map` (celui du serveur), dérivations documentées.
2. **Troupes du StateView en OBJETS `{id, owner}`** : le prompt écrit `troops []TroopID`
   en raccourci, mais le contrat `state.json` (architecture §5 :
   `[{ "id": "TR1", "owner": "P1" }]`) et le front (`Troop { id, owner }`, coloration par
   `troop.owner`) exigent des objets. Conforme au contrat, le front n'est pas modifié.
3. **Couverture `territories` du StateView : TOUS les territoires** (cohérent avec
   `TerritoryStates` exhaustif exigé par `Validate`) ; le panneau détail du front affiche
   « Personne / 0 R » sur les cases vides — comportement souhaité pour une démo.
4. **Cache partagé `/api/map` ↔ `/api/state`** : `mapResolver` cache désormais
   `mapgen.MapData` (au lieu des bytes) ; le handler map marshal à la demande (déterministe
   : `MapData` ne contient aucune map, octets identiques au marshal répété). Le résolveur
   d'état réutilise ce `MapData` → la carte n'est JAMAIS régénérée pour `/api/state`.
   Cache bytes du StateView séparé, clé = players (le seed est fixe par résolveur).
5. **`projectState` NON exporté** (comme le prompt) → le résolveur d'état vit dans
   `internal/api` : `StateResolver(...)` en closure (appelle `demo.DemoState` +
   `demo.DemoFreshness` + `projectState`, cache les bytes). `main.go` ne fait que câbler.
   L'import `api → engine/demo` est accepté. `api/state.go` documente en remarque de code
   que `/api/state` est un état d'exemple STATIQUE, le résolveur dynamique réel étant P1.7.
6. **Trigrammes nobles** : dérivés du prénom (3 premières lettres, majuscules, pliage
   d'accents É→E via une petite table — pas de dépendance externe). `prenoms.csv` a des
   codes de colonne uniques (assetgen l'impose) MAIS les trigrammes dérivés collisionnent
   (Bérenger/Bernier/Berthe/Bertrand → BER) : tirer les prénoms SANS remise et SAUTER les
   candidats dont le trigramme est déjà pris dans la partie. Validation finale par
   `models.Validate` (codes nobles uniques).
7. **Expansion du contrôle** : château + 1-2 voisins (compte seedé) via `Adjacencies` de
   mapData, en ÉVITANT les cases `village: true` (elles restent neutres, infra village
   intacte) et les cases déjà attribuées à un autre joueur. Repli BFS (voisins des voisins)
   si un château est enclavé. Échelle 8 territoires/joueur, villages = joueurs+1 → toujours
   faisable en pratique ; erreur explicite si irréalisable.
8. **Couleurs joueurs** : palette fixe de 5 hex (reprise des valeurs `PLAYER_PALETTE` du
   front : `#a84632`, `#2d5f9e`, `#7052a1`, `#34775c`, `#ad7a25`) affectée par index. Le
   StateView ne transporte pas les joueurs ; le champ `Player.Color` est rempli pour la
   complétude du modèle.
9. **Déterminisme à la construction** : toutes les collections sont construites dans un
   ordre déterministe (slices, jamais d'itération de map). Les maps sérialisent leurs clés
   triées au marshal JSON → octets identiques d'un appel à l'autre.

## Étapes

### 1. `internal/engine/demo` (NOUVEAU) — cœur du prompt

Fichiers : `internal/engine/demo/demo.go`, `internal/engine/demo/demo_test.go`.

`demo.go` :

- Helper RNG (sha256 + PCG, copie du pattern `mapgen/rng.go`, commentaire de référence).
- `func DemoState(seed string, assets assetgen.Assets, mapData mapgen.MapData,
  players int) (*models.GameState, error)` — pure, déterministe, sans I/O ni état global :
  - validation `players ∈ 2..5`, mapData non vide ;
  - `GameState` : `ID: "demo"`, `Seed: seed`, `Turn: 5`, `Season: models.SeasonForTurn(5)`
    (= spring, cohérence validée par `Validate`), collections non nil ;
  - `Territories` construits depuis `mapData` (ID, Code, Name, Terrain, Adjacencies
    franchissables — symétrie garantie par mapgen) ;
  - joueurs `P1..P<N>` : noms tirés de `assets.Prenoms` (shuffle seedé), couleurs
    palette fixe (décision 8) ;
  - départs : shuffle seedé des cases `Village == true` ; un territoire de départ DISTINCT
    par joueur ; château `InfraTypeCastle` niv. 1 construit DESSUS et REMPLAÇANT le
    village (jamais deux infras par case) ; `OwnerID` du territoire = joueur ; repli si
    plus de joueurs que de villages : tout territoire existant non pris (choix seedé) ;
  - contrôle 2-3 territoires PAR JOUEUR : château + 1-2 voisins seedés (décision 7) ;
    `Resources: 3` sur la case du château, 0 ailleurs ;
  - nobles `N1..` : un par joueur, `Code` = trigramme dérivé du prénom dédupliqué
    (décision 6), `Name = "{Prénom} de {Nom de commune du territoire château}"`,
    `LocationID` = case du château ;
  - troupes `TR1..` (compteur GLOBAL, convention du prompt) : 1 armée de 1 troupe sur la
    case du château + 1 armée de 2 troupes sur une case contrôlée voisine (1 seule armée
    si le joueur n'a qu'un territoire — repli) ; `Matricule` 1..n unique par joueur ;
  - villages non-départs : chaque flag `village: true` restant → infra `village` niv. 1
    sur territoire NON contrôlé (OwnerID nil), aucun château dessus ;
  - infras supplémentaires réparties seedées : 1 moulin, 1 tour de guet, 1 dépôt de
    vivres, chacune sur une case SANS infrastructure (règle de la structure unique),
    préférence cases contrôlées non-château ; IDs `I1..` séquentiels ;
  - `TerritoryStates` : une entrée EXACTEMENT par territoire (exigé par `Validate`),
    double indexation (les listes `Troops`/`Infrastructures` d'un état citent les entités
    qui pointent vers ce territoire) ;
  - `gs.Validate()` AVANT retour, erreur sinon.
- `func DemoFreshness(gs *models.GameState) map[models.TerritoryID]int` — déterministe :
  tour courant pour TOUTES les cases SAUF 1-2 territoires témoins (compte et choix seedés
  via `gs.Seed`) à `Turn − 2`.

`demo_test.go` (tests listés par le prompt) :

- même seed → même état byte-for-byte (2 appels `DemoState` + marshal, égalité des bytes) ;
- nb de joueurs/armées/troupes/nobles conforme (players paramétrable 2..5) ;
- toutes les références existent (troupes, nobles, infras, contrôles, stocks → territoires
  de mapData) ; aucun doublon d'ID ;
- contrôle de 2 à 3 territoires PAR JOUEUR ; au moins 1 troupe par joueur (GDD §2) ;
- un château par joueur, aucun doublon d'infrastructure par case ;
- chaque flag `village: true` de mapData matérialisé (village OU château de départ) ;
- noblesse : trigrammes uniques (y compris les cas de collisions type BER) ;
- round-trip JSON de `GameState` sans perte ;
- `DemoFreshness` déterministe et bornée (asOf ∈ {turn, turn−2}).
- Assets réels via `assetgen.Load("../../../assets")` + `mapgen.Generate` (pattern de
  `cmd/server/main_test.go`) + une petite `MapData` artisanale VALIDE pour le repli
  « plus de joueurs que de villages ».

### 2. `internal/api` — DTO et handler

Fichiers : `internal/api/state.go`, `internal/api/state_test.go`.

`state.go` :

- Types du DTO avec tags JSON conformes au contrat `state.json` (architecture §5) :
  `StateView { turn int, season Season, asOf map[models.TerritoryID]int,
  territories []TerritoryView, nobles []NobleView }` ;
  `TerritoryView { id, owner *models.PlayerID (null si neutre), resources int,
  troops []TroopView, infrastructures []InfraView }` ;
  `TroopView { id, owner }` ; `InfraView { type, level }` ;
  `NobleView { id, name, owner, location }`.
- `func projectState(gs *models.GameState, freshness map[models.TerritoryID]int)
  StateView` (NON exporté) : imbrique troupes et infrastructures PAR territoire
  (résolution via `TerritoryStates` → `gs.Troops` / `gs.Infrastructures`), ajoute
  `owner`/`asOf`, met en forme les nobles. Ordre des territoires = ordre de
  `gs.Territories` (déterministe).
- `func StateHandler(resolve func(players int) ([]byte, error)) http.HandlerFunc` —
  miroir de `MapHandler` (mêmes 400/500, même Content-Type), réutilise `requestedPlayers`
  (défaut 4, borné 2..5).
- `func StateResolver(mapData func(players int) (mapgen.MapData, error), seed string,
  assets assetgen.Assets) func(players int) ([]byte, error)` — closure : récupère le
  `MapData` partagé (cache côté main), exécute `demo.DemoState` + `demo.DemoFreshness` +
  `projectState`, marshal, cache bytes par players. Remarque de code : endpoint dev
  statique, le résolveur dynamique (rapports, hotseat) est P1.7.

`state_test.go` :

- `projectState` sur un `GameState` artisanal valide : structure et types JSON conformes
  au contrat (dé/marshaling en `map[string]any` et en types Go) ;
- `asOf ∈ {turn, turn−2}` sur toute la carte ;
- imbrication cohérente : une troupe listée pour un territoire y est réellement
  positionnée (`Troop.TerritoryID`), idem infrastructures ;
- handler : défaut 4, bornes 2..5, `400` invalide, `500` sur erreur résolveur (miroir de
  `map_test.go`).
