# Prompt P1.2f — État d'exemple (demo state) au front

```
Tu travailles sur "Crown & Borough". P1.2a→P1.2e sont faits : vocabulaire
troupe/armée, villages, nommage communes, géométrie/graphe v2, règles
vivrières documentées. La génération de carte existe (internal/engine/
mapgen, GET /api/map?players=N), les modèles aussi (internal/models), le
front (MapViewer) consomme un STUB d'état (web/src/fixtures/state.ts) qui
laisse la couche vivante vide.
Références : specs/architecture.md (contrat state.json), specs/roadmap.md
(P1.7 : endpoints dev /api/map + /api/state + /api/orders), specs/gdd.md.

Tâche : générer un ÉTAT D'EXEMPLE (demo game state) déterministe sur la
vraie carte générée et le brancher au front, pour vérifier manuellement que
les fonctionnalités d'affichage de la couche vivante ne sont pas cassées
pendant la suite du développement. Le STUB d'état statique du front
(web/src/fixtures/state.ts) est remplacé par cet état réel.

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais ; contenu de jeu en français.
Déterminisme : même seed → même état byte-for-byte.

1. GÉNÉRATEUR D'ÉTAT D'EXEMPLE (nouveau package internal/engine/demo) :
   - Signatures :
     * func DemoState(seed string, assets assetgen.Assets,
       mapData mapgen.MapData, players int) (*models.GameState, error) —
       pure, déterministe, sans I/O ni état global ;
     * func DemoFreshness(gs *models.GameState)
       map[models.TerritoryID]int — fraîcheur (asOf) par territoire,
       déterministe : tour courant pour toutes les cases SAUF 1-2
       territoires témoins (choix seedé) à tour courant − 2, pour
       vérifier le rendu "stale"/fraîcheur au front.
   - Utilise le MÊME seed que la carte (ou un dérivé documenté) : l'état
     d'exemple correspond toujours à la carte servie par /api/map.
   - VILLAGES MATÉRIALISÉS : chaque territoire de mapData portant le flag
     `village: true` reçoit une entité Infrastructure de type village
     (sans propriétaire — le champ OwnerID n'existe plus depuis P1.2b).
   - Contenu (mise en scène "milieu de partie") :
     * GameState : Turn 5, Season spring, Seed = le seed ;
     * players joueurs (défaut 4, borné 2..5) : IDs "P1".., noms tirés de
       prenoms.csv (ex. "Hugues", "Aliénor"), couleurs distinctes ;
     * CHAQUE joueur :
       - un territoire de départ DISTINCT portant un VILLAGE de la carte
         (P1.2b) où un CHÂTEAU a été construit (InfraType castle) — le
         château REMPLACE le village sur cette case (P1.2b : jamais deux
         infrastructures par case) ; le territoire est contrôlé par le
         joueur ; la répartition des départs est seedée (s'il y a plus de
         joueurs que de villages, repli : tout territoire existant) ;
       - contrôle de 2 à 3 territoires PAR JOUEUR (le château + 1-2
         voisins via le graphe de mapData adjacencies) ;
       - 1 noble (noble.id "N1".., code trigramme du prénom, nom
         "{Prénom} de {Nom de commune}", position = case du château) —
         prénoms tirés SANS remise et trigrammes DÉDUPLIQUÉS (prenoms.csv
         contient des doublons de trigrammes, ex. BER) : les codes nobles
         doivent être uniques sur toute la partie (validation modèles) ;
       - des troupes (convention "TR1"..) réparties en armées : 1 armée de
         1 troupe sur la case du château, et 1 armée de 2 troupes sur une
         case voisine (un joueur peut en avoir 1 seule si le nombre de
         territoires est limité) ;
       - un stock de ressources initial (TerritoryState.Resources, ex. 3)
         sur la case du château ;
     * quelques infrastructures supplémentaires réparties déterministement
       (toujours respecter la règle de la structure unique : au plus une
       par case) : 1 moulin (sur le château ou une case adjacente), 1 tour
       de guet, 1 dépôt de vivres ;
     * les villages non choisis pour le départ restent NON contrôlés
       (OwnerID nil du territoire) avec leur infrastructure village
       intacte, aucun château dessus ;
     * cohérence : toute référence (troupe, noble, infra, contrôle, stock)
       porte sur un territoire EXISTANT de mapData ; aucun doublon d'ID ;
       troupes au moins 1 par joueur (GDD §2 : départ avec au moins une
       armée).
   - Tests (internal/engine/demo/demo_test.go) : même seed → même état ;
     nb de joueurs/armées/troupes conforme ; toutes les références
     existantes ; contrôle de 2 à 3 territoires PAR JOUEUR ; un château
     par joueur, aucun doublon d'infrastructure par case ; chaque flag
     `village: true` de mapData matérialisé (sauf les cases de départ où
     le château l'a remplacé) ; noblesse : trigrammes uniques ; round-trip
     JSON de GameState sans perte ; fraîcheur (DemoFreshness) déterministe
     et bornée (asOf ∈ {turn, turn−2}).

2. ENDPOINT DEV GET /api/state (avec DTO EXPLICITE) :
   - Le contrat state.json (specs/architecture.md §5) n'est PAS produit par
     le marshaling direct d'un GameState : les modèles sérialisent les
     TerritoryStates en map keyée par ID, les armées/troupes et
     infrastructures à plat, et ne transportent pas d'asOf (champ différé
     à P2, p1.1). Il faut donc un DTO de projection :
     * type StateView (dans internal/api, JSON tags selon le contrat
       state.json) : turn, season, asOf map[territoire]turn,
       territories []{ id, owner, resources, troops []TroopID,
       infrastructures []{type, level} }, nobles []{id, name, owner,
       location} ;
     * projection : func projectState(gs *models.GameState, freshness
       map[models.TerritoryID]int) StateView — imbrique troupes et
       infrastructures PAR territoire, ajoute owner/asOf, met en forme les
       nobles. GameState reste SANS asOf (réservé à P2).
   - Handler : GET /api/state?players=N (défaut 4, borné 2..5) → génère
     DemoState + DemoFreshness (même seed que /api/map), projette le
     StateView, renvoie le JSON ; cache mémoire (seed, players) partagé
     avec /api/map pour ne pas régénérer la carte.
   - Le résolveur final /api/state "dynamique" (rapports, hotseat) reste
     P1.7 : ici c'est un état d'exemple statique, documenté comme tel dans
     une remarque de code.
   - CORS déjà en place ; /healthz inchangé.
   - Tests (internal/api) : StateView conforme au contrat (structure et
     types) ; asOf ∈ {turn, turn−2} ; imbrication cohérente (une troupe
     listée pour un territoire y est vraiment positionnée).
```
