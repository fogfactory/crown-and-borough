# Prompt P2.2 — Messagers et rapports : vision T-x (fog of war)

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le moteur existe (P1.4/P1.5/P1.6 : résolution, ravitaillement, hiver ; P2.1 :
soutien automatique), les modèles (P1.1), le parser (P1.3), le cycle de jeu et
le TurnReport (P1.7, rapport GLOBAL — le filtrage par joueur arrive ICI),
l'API dev hotseat (P1.7 : /api/map, /api/state, /api/orders).
Références : specs/gdd.md (§2 Réception des rapports, §3 Vitesse des
messagers, §4 Latence d'Information) et specs/architecture.md (§5 contrats
map.json/state.json — le champ asOf y est PRÉVU).

PÉRIMÈTRE : vision par joueur — la fraîcheur de l'information (T0 vs T-x)
par territoire, state.json devient une VUE PAR JOUEUR (asOf par territoire).
La transmission différée des ORDRES (P2.3) est HORS périmètre (les ordres
restent instantanés, vision T0 pour la soumission). L'interception des
rapports par l'ennemi est HORS périmètre (les messagers passent partout,
choix documenté).

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. PRINCIPE (GDD §4) : le joueur voit l'état le plus récent apporté par ses
   messagers : pour chaque territoire X, sa vue = l'état de X tel qu'il
   était il y a travelTime(X) tours. Le rapport de X se déplace à la
   vitesse du terrain vers les RÉCEPTEURS du joueur (sa Capitale et ses
   Nobles — les récepteurs se déplacent avec les nobles).

2. TEMPS DE TRAJET (GDD §3) :
   - Coût par case traversée (durée du rapport sur cette case) :
       plaine = 0,5 tour (2 cases/tour) | route (arête) = 0,5 | forêt =
       1 tour | colline = 1 tour | montagne = 2 tours | marécage = 2 tours
   - Relais de Poste (post_relay) sur une case : la vitesse des messagers y
     est DOUBLÉE → coût de la case divisé par 2
   - travelTime(X) = plus court chemin de X vers le récepteur le plus
     proche (Dijkstra sur le graphe d'adjacence, coûts ci-dessus, départage
     ID croissant) ; asOf(X) = Tour courant − ceil(travelTime)
   - asOf < 0 → territoire INCONNU (aucun rapport reçu : la vue ne montre
     rien, ni contrôle, ni unités, ni stock)

3. VISION T0 (GDD §4) — asOf = tour courant, état EXACT :
   - la case de la CAPITALE du joueur (le château désigné)
   - les cases où se trouve un NOBLE du joueur (libre OU prisonnier — le
     joueur sait où sont ses nobles ; un noble PRISONNIER donne la vision
     T0 au ravisseur sur SA case, pas au propriétaire — chois : la vue du
     ravisseur, documenté)
   - les cases avec une TOUR DE GUET du joueur ET leurs cases ADJACENTES
   - les armées du joueur : leurs POSITIONS (territoire + taille de pile)
     sont toujours connues exactement (ce sont ses troupes — mais le RESTE
     de l'information de ces cases suit la règle asOf)

4. VUE PAR JOUEUR (internal/engine, fonction PURE, déterministe, sans I/O) :
   - BuildPlayerState(game *models.GameState, playerID PlayerID) PlayerView
   - PlayerView = version FILTRÉE du state.json (contrat architecture §5) :
     par territoire — owner, armies, infrastructures, resources, SEULEMENT
     si asOf ≥ 0 (sinon "unknown") ; TOUJOURS asOf (le tour de la
     génération de l'information, = 0 pour T0)
   - L'information filtrée est celle de l'état du tour asOf (pas l'état
     courant déguisé) : BuildPlayerState doit donc soit rejouer l'état au
     tour asOf (si les états passés sont conservés en mémoire — dev), soit
     documenter qu'au MVP dev les états passés sont gardés (anneau
     d'historique en mémoire, taille configurable) — CHOISIS une approche
     déterministe et testable, documente-la
   - La vue par joueur ne modifie JAMAIS le GameState (les résolutions
     restent sur l'état réel complet)

5. API DEV (P1.7) : GET /api/state?player=P1 (ou player=P1&asOf=tout) →
   la PlayerView du joueur ; GET /api/state sans paramètre → vue GLOBALE
   (dev, asOf = 0 partout) ; le TurnReport (P1.7) reste GLOBAL au MVP
   (choix documenté : le rapport n'est pas encore filtré par joueur)

6. FRONT (web/) :
   - GET /api/state?player=<sélecteur joueur existant> → rendu par
     territoire : badge de fraîcheur ("il y a N tours" ou "inconnu" pour
     asOf < 0), estompage des territoires périmés, superposition exacte
     pour les T0
   - les positions des armées du joueur restent toujours visibles
   - aucun changement au map.json (la géométrie reste commune à tous)

7. TESTS (internal/engine/vision_test.go) :
   - travelTime : plaine 2 cases = 1 tour ; forêt 2 cases = 2 tours ;
     montagne = 2 tours/case ; route = 0,5 ; chemin mixte (plaine+montagne)
     = somme exacte ; ceil appliqué (0,5+0,5+0,5 = 1,5 → asOf T−2)
   - Relais : case à relais = coût divisé par 2 (2 cases plaine dont une à
     relais = 0,75 → ceil 1 → asOf T−1 au lieu de T−2)
   - T0 : capitale ; noble (libre) ; noble PRISONNIER → T0 pour le ravisseur
     seulement ; tour de guet + ses adjacentes ; hors de ces cas → asOf
     normal
   - asOf < 0 → unknown (armées, contrôle et stock absents de la vue)
   - Positions des armées du joueur visibles même si asOf < 0
   - VUES DIFFÉRENTES : deux joueurs voient des états différents (le côté
     de l'adversaire est périmé chez l'un et pas chez l'autre) ; la vue
     globale dev reste complète
   - DÉTERMINISME : deux appels BuildPlayerState sur le même état →
     vues identiques ; les résolutions (Resolve/ResolveWinter) ne sont PAS
     affectées par la vue (l'état réel reste complet)

Critères d'acceptation :
- make test passe ; make vet passe ; aucune dépendance tierce ajoutée
- BuildPlayerState est pure et déterministe ; l'état réel du jeu n'est
  jamais muté par la vue
- La fraîcheur (asOf) est calculée depuis le graphe et les récepteurs
  courants (capitale + nobles + tours), pas stockée par événement
- Le front affiche la carte avec fraîcheur par territoire

Note : documente dans ta réponse finale les choix ouverts que tu as tranchés
```
