# Plan d'implémentation P1.2g — Armée : entité unique par territoire (owner + taille)

Brief d'exécution autonome pour un modèle d'implémentation (ligne de commande, mode build, sans intervention de l'utilisateur).

## Contexte

Le prompt P1.2g (specs/prompts/p1.2g-armee-unique-territoire.md) remplace la modélisation
« troupe individuelle » (`Troop`/`TroopID`/`Matricule`) par une **armée unique par
territoire** : `Army { ID, OwnerID, TerritoryID, Size }`, compteur global `"A1"..`, stockée
au niveau du `GameState` (liste `Armies`) et référencée par le territoire (`Army *ArmyID`).
Le contrat `state.json` (§5 architecture) devient `"army": { "owner": "P1", "size": 2 }` —
sans id côté front, adressage par territoire. Le départage GDD §4/§8 passe du matricule au
trigramme du TERRITOIRE (ordre lexicographique).

Références : `specs/architecture.md` §5 (contrat state.json) et §6 (ordres : réception,
dispersion, sans ordre), `specs/gdd.md` §4/§5/§6/§8, `specs/roadmap.md` (ligne P1.2g),
`specs/prompts/p1.7-rapport-tour-hotseat.md` et `specs/prompts/p1.2a-vocabulaire-troupe-armee.md`
(dérogation de vocabulaire), `specs/plans/p1.2f-implementation-plan.md` (convention de format).

## Difficulté et modèle recommandé

Faible : refactor mécanique d'un modèle récent et bien testé, sans nouvelle règle de jeu
ni changement de forme des endpoints. Tous les fichiers concernés sont identifiés
(recensement exhaustif fait — zéro référence `Troop` hors périmètre) ; les étapes sont
indépendantes les unes des autres et chacune se vérifie par tests. Aucun risque de blocage.

## Décisions de conception

1. **Front sans id** : `ArmyView { Owner, Size }` — PAS de champ `id` dans le DTO.
   `TerritoryView.Army *ArmyView` avec tag `json:"army"`, SANS `omitempty` (toujours
   sérialisé ; `null` si pas d'armée). Adressage par le territoire (GDD : réception
   « l'armée de la case »).
2. **Le modèle garde l'ID** : `Army.ID` (compteur global `"A%d"`) est conservé pour
   l'évolution future (ordres, rapports) ; il n'est simplement pas projeté dans le DTO.
   Le numéro d'ID ne reflète plus la taille (contrat n'exigeant que `owner` + `size`).
3. **Départage par trigramme du territoire** : l'ordre lexicographique des codes de
   territoires (GDD §8) remplace le matricule partout dans les docs (GDD §4, §8,
   architecture §6).
4. **Demo : repli 1 armée** : si le joueur ne contrôle qu'un territoire (aucune case
   contrôlée voisine), une seule armée (taille 1) est placée sur le château — supprime
   l'erreur `cannot place a second army on a territory without adjacent controlled
   territory`. La construction devient toujours faisable.
5. **Périmètre docs strict** : seuls `specs/architecture.md`, `specs/gdd.md`,
   `specs/roadmap.md`, `specs/prompts/p1.7-rapport-tour-hotseat.md` et
   `specs/prompts/p1.2a-vocabulaire-troupe-armee.md` sont réécrits (dérogation P1.2a
   étendue). Tous les autres fichiers specs restent tels quels ; zéro « matricule »
   résiduel exigé dans gdd.md et architecture.md.

## Étapes

### 0. Sauvegarde du plan

Ce fichier (`specs/plans/p1.2g-implementation-plan.md`), convention de la collection
`specs/plans/` (format p1.2f).

### 1. `internal/models` — refactor du modèle

Fichiers : `internal/models/entities.go`, `internal/models/gamestate.go`,
`internal/models/enums.go`, `internal/models/models_test.go`.

`entities.go` :

- `TroopID` → `ArmyID` ; `Troop` → `Army { ID ArmyID; OwnerID PlayerID; TerritoryID
  TerritoryID; Size int }` avec tags JSON `"id"`, `"owner"`, `"territory"`, `"size"` ;
- suppression de `Matricule` ; commentaires « A* ids are retired » retirés/corrigés ;
- `TerritoryState.Troops []TroopID` → `TerritoryState.Army *ArmyID` avec tag
  `json:"army"` (pointeur nil = pas d'armée) ;
- note de code : adressage par territoire, départage par trigramme du territoire
  (référence GDD §8).

`gamestate.go` :

- `GameState.Troops []Troop` → `GameState.Armies []Army` avec tag `json:"armies"` ;
- `Validate()` §5 : ids uniques, `OwnerID`/`TerritoryID` référents existants, `Size >= 1`,
  double indexation (chaque armée de `Armies` référencée par le `TerritoryState.Army` de
  son territoire ET réciproquement — chaque `TerritoryState.Army` pointe vers une armée
  de `Armies` dont le `TerritoryID` est celui-ci) ;
- `Validate()` §8 : contrôle du pointeur `TerritoryState.Army` (comme les stocks) ;
- enums.go : commentaire de package « troops » → « armies ».

`models_test.go` :

- `validState` : `A1`, `A2` (tailles {1, 2}), champs `Armies`/`Army` au lieu de
  `Troops`/`Troop` ; tests matricule supprimés ou adaptés (le numéro ne reflète plus la
  taille) ;
- round-trip JSON : clés `"armies"` (liste) et `"army"` (pointeur, `null` sans armée) ;
- nouveaux cas d'erreur : `Size == 0` ; armée présente dans `Armies` sans référence
  dans son territoire ; `TerritoryState.Army` pointant vers un id inconnu ou une armée
  d'un autre territoire (double indexation incohérente).

Vérification : `make test && make vet`.

### 2. `internal/engine/demo` — construction des armées

Fichiers : `internal/engine/demo/demo.go`, `internal/engine/demo/demo_test.go`.

`demo.go` :

- `addTroop` → `addArmy(gs, owner, territory, size)` avec compteur global `"A%d"` ;
  `controlledTroopLocation` → `controlledArmyLocation` (case contrôlée voisine du
  château, choix seedé) ;
- construction : 1 armée `Size 1` sur le château + 1 armée `Size 2` sur une case
  contrôlée voisine ; **repli** : si aucune case contrôlée voisine → une seule armée
  `Size 1` (décision 4) ; `state.Troops` → `state.Armies` ;
- `TerritoryStates` : `Troops`/`Army` → pointeur `&armyID` sur le territoire concerné
  (nil ailleurs).

`demo_test.go` :

- `armies == players*2` (ou `players` si repli) ; tailles `{1, 2}` (ou `{1}`) ;
  ≥ 1 armée par joueur (GDD §2) ; ids uniques ; ≤ 1 armée par case ; chaque
  `TerritoryState.Army` référence une armée dont `TerritoryID` = ce territoire ;
- nb de troupes total = somme des tailles ; round-trip JSON sans perte ;
- adapter les tests existants (`players*3 armies` → `players*2 armies` par exemple).

Vérification : `make test && make vet`.

### 3. `internal/api` — DTO et projection

Fichiers : `internal/api/state.go`, `internal/api/state_test.go`.

`state.go` :

- `TroopView` supprimée ; `ArmyView { Owner models.PlayerID `json:"owner"`; Size int
  `json:"size"` }` (SANS id — décision 1) ;
- `TerritoryView.Troops []TroopView` → `TerritoryView.Army *ArmyView` `json:"army"`
  (sans `omitempty`) ;
- `projectState` : résolution via `TerritoryStates` → `gs.Armies` (index
  `map[models.ArmyID]models.Army`) ; pointeur nil si aucune armée.

`state_test.go` :

- contrat : `"army"` nullable, `{ "owner": "P1", "size": 2 }`, aucune clé `"id"` dans
  l'armée (dé/marshaling en `map[string]any` et en types Go) ;
- imbrication cohérente : l'armée listée pour un territoire y est réellement positionnée
  (`Army.TerritoryID`) ; handler inchangé (défaut 4, bornes 2..5, 400/500).

Vérification : `make test && make vet`.

## Vérifications finales (critères d'acceptation du prompt)

1. `make test` passe (modèles + demo + api + mapgen) ; `make vet` passe.
2. Greps zéro résidu : `rg -n 'Troop|Matricule|matricule' internal/ web/src` → aucune
   occurrence ; `rg -n '"TR[0-9]' internal/ web/src` → aucune ; dans les 5 docs réécrits :
   `rg -n 'matricule|TR1'` → aucune.
3. `cd web && npm run build && npm run lint` passent.
4. `make run` : `GET /api/state?players=4` renvoie un JSON conforme au contrat
   (`"army": { "owner", "size" }` ou `null`, aucune clé `"id"` d'armée) et cohérent avec
   `GET /api/map?players=4` (mêmes territoires, même seed) — vérification manuelle.
5. `make web-dev` : une seule pastille par case contrôlée, badge `×N` visible, panneau
   « Armée », aucune erreur console — vérification manuelle.
