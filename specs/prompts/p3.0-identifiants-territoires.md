# Prompt P3.0 - Contrat territorial fondé sur les trigrammes

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le moteur P1/P2, l'API REST et la persistance JSON sont les prochaines couches
du produit. Les territoires possèdent actuellement un matricule interne de
type TerritoryID (`T24`) et un code de commune/trigramme (`ROS`). Le retour de
test confirme que seul le trigramme a un sens pour une case de jeu.
Références : specs/gdd.md, specs/architecture.md, specs/roadmap.md,
specs/prompts/p1.10-poste-commandement-rapport.md et les contrats map.json et
state.json.

PÉRIMÈTRE : faire du trigramme territorial l'identifiant unique du domaine et
des contrats publics. Cette étape doit être terminée avant P3.1, afin que les
contrats de l'API REST et de la persistance ne figent pas le matricule.

RÈGLE DE CODE : code, identifiants, commentaires et messages techniques en
anglais. Les labels de jeu et de l'interface restent en français.

1. IDENTITÉ TERRITORIALE :
   - Supprimer le double concept TerritoryID/Code pour les territoires.
   - Utiliser un type de code territorial explicite, fondé sur le trigramme
     unique, dans les modèles, les index et les références métier.
   - Ne plus générer ni exposer de matricule séquentiel `T<number>`.
   - Les trigrammes restent exactement trois lettres majuscules, uniques dans
     une carte et stables pour une seed donnée.
   - Les identifiants internes des armées, nobles, infrastructures, chaînes et
     ordres peuvent rester distincts : cette tâche concerne uniquement les
     territoires.

2. MODÈLE ET MOTEUR :
   - Adapter Territory, GameState et TerritoryStates pour que les clés et les
     références utilisent le trigramme.
   - Adapter les adjacences, les positions d'armées et de nobles, les
     infrastructures, les chaînes, les ordres, les dispersions et tous les
     événements de résolution.
   - Adapter les index, helpers, BFS, génération de carte, résolution,
     ravitaillement, hiver, rapports et tests sans conserver un champ miroir
     uniquement pour compatibilité.
   - Remplacer les comparaisons ou départages qui utilisent accidentellement
     le matricule par le trigramme lorsque la règle demande un ordre
     territorial.

3. CONTRATS API ET FRONT :
   - Le map.json et le state.json ne doivent plus contenir un `id` territorial
     séparé du trigramme. Utiliser un champ et un nom cohérents documentés
     dans specs/architecture.md.
   - Adapter les DTO Go, les types TypeScript, les clés React, les attributs
     data-territory et les tooltips.
   - Les labels, erreurs et rapports affichent directement les trigrammes.
   - Mettre à jour les fixtures et les exemples qui contiennent `T<number>`.

4. PERSISTANCE ET MIGRATION :
   - P3.0 précède la persistance P3.3 : aucune compatibilité avec une partie
     persistée utilisant les anciens matricules n'est requise au MVP.
   - Si un format intermédiaire est nécessaire pour les tests, il doit être
     explicitement temporaire et ne pas réintroduire le double identifiant
     dans les contrats finaux.

5. TESTS ET DOCUMENTATION :
   - Vérifier l'unicité, la forme et la stabilité des trigrammes.
   - Vérifier le round-trip JSON des cartes, états et rapports.
   - Vérifier une résolution complète, un hiver, un ravitaillement et une
     génération de carte après le refactor.
   - Rechercher et supprimer toute exposition utilisateur de `T<number>`.
   - Mettre à jour specs/gdd.md, specs/architecture.md et specs/roadmap.md.
   - Exécuter go test ./..., go vet ./..., npm run build et npm run lint.

Critères d'acceptation :
- Un territoire n'a plus qu'une identité : son trigramme.
- Les modèles, le moteur, l'API, la persistance prévue et le front sont
  cohérents avec cette identité.
- Aucun `T<number>` n'est généré ou exposé dans les contrats finaux.
- Les tests de déterminisme et de résolution passent.

Ne commite pas sans instruction explicite. Lorsqu'un commit et un push sont
demandés, mets à jour specs/roadmap.md juste avant le commit avec le statut
réel de P3.0, inclus cette mise à jour dans le commit, puis pousse l'ensemble.
Ne laisse pas P3.0 au statut « Prompt écrit » après sa livraison.
```
