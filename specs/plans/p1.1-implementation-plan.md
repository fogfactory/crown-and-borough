# Plan P1.1 — Modèles métier Go (à déléguer)

Brief d'exécution autonome pour un modèle d'implémentation.

## Contexte

Squelette P0.1 + assets P0.2 en place : `cmd/server` (charge les assets au
démarrage), `internal/{api,engine,models}` vides (`.gitkeep`),
`internal/db/assetgen` (loader CSV — style de référence : commentaires anglais,
erreurs `assetgen: <context>: <reason>`), Go 1.26, zéro dépendance tierce,
Makefile (`test` = `go test ./...`, `vet` = `go vet ./...`). Le prompt source
est `specs/prompts/p1.1-modeles-metier.md` — le lire en entier avant de
commencer. Références : `specs/gdd.md` (§2 tours/saisons, §5 piles, §7
infrastructures, §8 famine), `specs/architecture.md` (§4 convention de code, §5
contrats map.json/state.json, §6 ordres — pour la place à prévoir, sans rien
implémenter).

Règles absolues :

- Code exclusivement en anglais (identifiants, commentaires, messages
  d'erreur) ; seules les chaînes de contenu de jeu sont en français.
- Stdlib uniquement (`encoding/json`, `fmt`). Aucune dépendance web, aucun ORM.
- Les noms de champs dictés par le prompt (`Matricule`, `IsLieuDit`,
  `TerritoryStates`…) sont repris **verbatim** — même traitement que
  `Qualificatif` en P0.2.
- Ne rien commiter.

## Difficulté et modèle recommandé

Difficulté **2/5** — structures de données pures + validation + tests (~700
lignes, stdlib). La rigueur porte sur les invariants (symétrie des adjacences,
double indexation cohérente) et la couverture des tests négatifs. Modèle budget
conseillé : Kimi K2 ou DeepSeek V3.x — coût estimé < 0,05 €.

## Décisions de conception (à appliquer et documenter dans le code)

1. **`TerritoryState.OwnerID` en `*PlayerID`** (`nil` = neutre, JSON `null`) —
   cohérent avec le prompt P1.5 qui teste `OwnerID ≠ nil`. Les `OwnerID` de
   Army/Noble/Infrastructure restent des `PlayerID` pleines (toujours
   possédés).
2. **`TerritoryStates` couvre TOUS les territoires** (1 entrée par territoire,
   imposé par `Validate()`) — le moteur n'aura jamais de lookup manquant.
3. **Double indexation validée** : `Army.TerritoryID` ↔
   `TerritoryStates[t].Armies` (idem infrastructures) — cohérence
   bidirectionnelle exigée.
4. **`TerritoryState.Infrastructures` : au plus une par case** — « Règle de
   la Structure Unique » (GDD §3), imposée par `Validate()`. Le pillage
   (GDD §6/§8) détruit l'infrastructure de la case sans choix ni champ de
   date (« l'infrastructure la plus récente » n'existe pas).
5. **Matricule unique par joueur** — le départage famine (§8) et la réception
   de chaîne (§6, « plus petit matricule ») s'appliquent au sein d'un même
   propriétaire.
6. **`Season` stockée mais validée contre `Turn`** :
   `Season == SeasonForTurn(Turn)`, `Turn ≥ 1`, `Year() = (Turn-1)/4 + 1`.
7. **Pas de `NewGame`** : la création de partie arrive en P1.2. Uniquement
   `NewGameState()` (collections vides non-nil, Turn 1, spring — JSON `[]`/`{}`
   plutôt que `null`).
8. **Rien pour la famine ni la fraîcheur** : la famine est transiente (flag
   dans la résolution P1.5, non persisté) et `asOf` arrive en P2.2. Seul
   `Army.Matricule` (déjà demandé) sert le départage.
9. **Pas de `CapitalCastleID`** (P1.6), pas de géométrie `points` (P1.2, côté
   mapgen), pas de chaîne d'ordres sur `Army` (P1.3 l'ajoutera — `army.chain`,
   cf. architecture §6).
10. **Codes validés** : territoire `^[A-Z]{3}$` si lieu-dit, `^[A-Z]{4}$`
    sinon ; noble `^[A-Z]{3}$` ; codes de territoires uniques sur la carte ;
    **codes de nobles uniques** — revirement post-implémentation : l'unicité
    des trigrammes de nobles est imposée par `Validate()` (deux nobles d'une
    même partie ne peuvent pas partager un prénom).

## Étape 1 — `internal/models/enums.go` (~80 lignes)

Doc de package en anglais (socle métier du moteur : Go pur, aucune dépendance
web/ORM). Trois enums chaînes typées, constantes, `IsValid()` :

```go
type Terrain string
const (
    TerrainPlain    Terrain = "plain"
    TerrainForest   Terrain = "forest"
    TerrainHill     Terrain = "hill"
    TerrainMountain Terrain = "mountain"
    TerrainSwamp    Terrain = "swamp"
)
func (t Terrain) IsValid() bool
```

- `Season` : `spring|summer|autumn|winter` + `IsValid()`.
- `InfraType` : `mill|post_relay|watchtower|supply_depot|castle` + `IsValid()`.
- `SeasonForTurn(turn int) Season` : `(turn-1)%4` → spring… (simple calcul de
  date, pas du moteur).
- Commentaires liant au GDD : terrain → vitesse des messagers (§3) ; infra →
  effets (§7, moulin +1 R/niveau).
- Sérialisation JSON naturelle (chaîne) ; **pas** de `UnmarshalJSON` custom :
  un point d'entrée de validation unique, `GameState.Validate()`.
- Piège à tester : `"any"` (qualificatifs.csv) n'est PAS un `Terrain` valide.

## Étape 2 — `internal/models/entities.go` (~100 lignes)

Types ID + entités, tags JSON alignés sur les contrats map.json/state.json
quand ils existent :

```go
type PlayerID string
type TerritoryID string
type ArmyID string
type NobleID string
type InfraID string

type Player struct {
    ID    PlayerID `json:"id"`
    Name  string   `json:"name"`
    Color string   `json:"color"`
}

type Territory struct {
    ID          TerritoryID   `json:"id"`
    Code        string        `json:"code"`
    Name        string        `json:"name"`
    Terrain     Terrain       `json:"terrain"`
    IsLieuDit   bool          `json:"lieuDit"`
    Adjacencies []TerritoryID `json:"adjacencies"`
}

type Army struct {
    ID          ArmyID      `json:"id"`
    Matricule   int         `json:"matricule"` // army number; famine tie-break (GDD §8)
    OwnerID     PlayerID    `json:"owner"`
    TerritoryID TerritoryID `json:"territory"`
}

type Noble struct {
    ID         NobleID     `json:"id"`
    Code       string      `json:"code"` // first-name trigram (GDD §6)
    Name       string      `json:"name"`
    OwnerID    PlayerID    `json:"owner"`
    LocationID TerritoryID `json:"location"`
}

type Infrastructure struct {
    ID          InfraID    `json:"id"`
    Type        InfraType  `json:"type"`
    Level       int        `json:"level"` // >= 1; mill yields +1 R per level (GDD §7)
    OwnerID     PlayerID   `json:"owner"`
    TerritoryID TerritoryID `json:"territory"`
}

type TerritoryState struct {
    OwnerID         *PlayerID `json:"owner"` // nil = neutral
    Resources       int       `json:"resources"`
    Armies          []ArmyID  `json:"armies"`
    Infrastructures []InfraID `json:"infrastructures"` // construction order, oldest first
}
```

Chaque entité commentée en lien avec le GDD (`Matricule` ↔ départage famine
§8 ; `IsLieuDit` ↔ production/stockage §3 ; château = lieu-dit synthétique §7 —
c'est la présence d'un château qui compte, pas un flag).

## Étape 3 — `internal/models/gamestate.go` (~250 lignes)

```go
type GameState struct {
    ID               string                         `json:"id"`
    Seed             string                         `json:"seed"`
    Turn             int                            `json:"turn"`
    Season           Season                         `json:"season"`
    Players          []Player                       `json:"players"`
    Territories      []Territory                    `json:"territories"`
    Nobles           []Noble                        `json:"nobles"`
    Armies           []Army                         `json:"armies"`
    Infrastructures  []Infrastructure               `json:"infrastructures"`
    TerritoryStates  map[TerritoryID]TerritoryState `json:"territoryStates"`
}

func NewGameState() *GameState // Turn 1, spring, collections non-nil
func (g *GameState) Year() int // (Turn-1)/4 + 1 (GDD §2)
func (g *GameState) Validate() error
```

`Validate()` fail-fast, erreurs anglaises préfixées `models: ` (style
assetgen), dans l'ordre :

1. Turn ≥ 1 ; Season valide et cohérente avec `SeasonForTurn(Turn)`.
2. Players : IDs uniques.
3. Territories : IDs uniques, codes uniques, terrain valide, format du code
   selon `IsLieuDit` (3/4 lettres A-Z).
4. Adjacences : cibles existantes, pas d'auto-adjacence, pas de doublon,
   symétrie stricte (A→B ⇒ B→A).
5. Armies : IDs uniques, matricule unique par joueur, owner existant,
   territoire existant, présence dans `TerritoryStates[t].Armies`.
6. Nobles : IDs uniques, code `^[A-Z]{3}$`, owner existant, location existante.
7. Infrastructures : IDs uniques, type valide, level ≥ 1, owner existant,
   territoire existant, présence dans `TerritoryStates[t].Infrastructures`.
8. TerritoryStates : couverture exacte (chaque territoire a son entrée, pas
   d'orpheline), owner nil ou existant, IDs d'armées/infras existants et
   cohérents dans les deux sens, Resources ≥ 0.

Helpers internes non exportés au besoin (ex. `indexTerritories`). **Pas** de
`NewGame`, **pas** de finders exportés (le moteur construira ses index en
P1.4).

## Étape 4 — Tests `internal/models/models_test.go` (~350 lignes)

Helper `validState()` : état complet valide (2 joueurs, 4 territoires en anneau
dont 1 lieu-dit, 2 armées, 1 noble, 1 moulin niveau 2 + 1 château, 1 territoire
neutre à owner nil, ressources) — base mutée pour les cas négatifs.

- `TestTerrainIsValid` / `TestSeasonIsValid` / `TestInfraTypeIsValid` :
  valides + invalides (`""`, `"MARSH"`, `"any"` pour Terrain, `"mill "` avec
  espace…).
- `TestSeasonForTurn` / `TestYear` : turn 1 → spring/an 1, turn 4 → winter/an
  1, turn 5 → spring/an 2.
- `TestValidateValidState` : l'état de référence passe.
- `TestValidateErrors` table-driven (nom, mutation, fragment du message
  attendu) : IDs dupliqués (territoire, armée, joueur), code dupliqué,
  matricule dupliqué même owner (+ cas valide : même matricule chez 2 owners),
  adjacence asymétrique / vers ID inconnu / auto-adjacence, armée/noble/infra
  référençant un territoire inexistant, owner inexistant, armée absente de la
  liste du TerritoryState (et inversement), entrée TerritoryState
  manquante/orpheline, terrain/season/infra invalides, level 0, ressources
  négatives, code lieu-dit 4 lettres, code non-lieu-dit 3 lettres, code noble 4
  lettres, season incohérente avec le turn, turn 0.
- `TestGameStateJSONRoundTrip` : état de référence → `json.Marshal` →
  `json.Unmarshal` → `reflect.DeepEqual` + `Validate()` du résultat ; vérifie
  aussi que `NewGameState()` sérialise les collections vides en `[]`/`{}`.
- `TestCodeInvariants` : 3 lettres lieu-dit / 4 sinon / 3 noble (via Validate
  sur mutations ciblées).
