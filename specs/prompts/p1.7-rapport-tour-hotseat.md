# Prompt P1.7 — Rapport de tour, cycle des saisons et boucle hotseat

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le moteur existe : Resolve (P1.4, phases 0-5, combat/ravitaillement),
ResolveWinter (P1.6, ordres d'hiver + bilan), le parser des chaînes (P1.3) et
des ordres d'hiver (P1.6), les modèles (P1.1), la génération de carte (P1.2),
assets/balance.json (P1.6), le squelette serveur Go (cmd/server, P0.1) et le
front Vite+React (P0.3, MapViewer sur fixtures).
Références : specs/gdd.md (§2 Cœur de Loop & Saisons), specs/architecture.md
(§5 contrats map.json/state.json, §6 ordres) et specs/roadmap.md (P1.7).

PÉRIMÈTRE : cycle des saisons + création de partie (setup initial), rapport
de tour (TurnReport) construit depuis les événements du moteur, endpoints dev
hotseat (/api/map, /api/state, /api/orders) et intégration front (boucle
locale). La persistance, l'auth, la vision T-x et le multi-utilisateur sont
P2/P3 — HOTSEAT = tout le monde joue sur la même machine, vision T0.

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu (noms, labels UI)
sont en français.

1. CYCLE DE JEU (internal/engine/game.go) :
   - CreateGame(seed string, players []PlayerInit, balance Balance, assets
     Assets) (*models.GameState, error) :
     * génère la carte (mapgen, P1.2) ; place chaque joueur sur un lieu-dit
       DISTINCT (déterministe par seed : lieux-dits triés par ID, un par
       joueur, répartition équitable — documente ton choix)
      * setup initial (GDD §2, P1.6) : château AUTOMATIQUE sans coût sur le
        lieu-dit de départ (capitale par défaut : premier château),
        starting_nobles noble(s) (nom = prénom tiré de prenoms.csv +
        "de <territoire>", code unique), starting_troops troupe(s)
        (matricules 1..N), starting_resources R dans le stock local
        (balance.json), contrôle du lieu-dit au joueur
   - ResolveTurn(game *models.GameState, balance Balance, orders
     OrdersInput) (TurnReport, error) — PURE :
     * dispatche selon la saison : winter → ResolveWinter ; sinon → Resolve
      * AVANCE le cycle des saisons (le câblage différé par P1.6 est FAIT
        ICI) : printemps → été → automne → hiver → printemps ;
        **game.Turn (tick absolu) incrémente À CHAQUE saison** (asOf P2.2,
        émissions et arrivées de messagers P2.3 s'appuient dessus) ;
        l'année = (Turn-1)/4 + 1 (l'hiver clôt l'année)
   - OrdersInput : { chains: [{player, noble, text}], winter: [{player,
     lines}] } — soumission d'un TOUR complet (hotseat : tous les joueurs
     à la fois) ; erreurs de parsing → erreur explicite avec numéro de
     ligne (aucun état modifié)

2. TURN REPORT (internal/engine/report.go) :
   - Construit UNIQUEMENT depuis Resolution.Events (+ éventuellement un
     snapshot d'état AVANT/APRÈS pour les compteurs) — aucun accès à la
     logique interne
   - Sections typées (JSON-serialisable, pas de formatage : le front rend) :
     * header : year, season, turn number
* players : par joueur — ressources (avant/après), troupes, nobles,
        infrastructures, contrôle (compteurs)
      * supply (P1.5) : par source — production, demande, stock consommé ;
        famines (armées, matricules, auto-pillages)
     * combats (P1.4) : par case contestée — contendents, forces, gagnant,
       statu quo, retraites, destructions, soutiens coupés
     * orders : par armée — ordre exécuté, outcome (success/failure/
       invalid), chaîne consommée/brisée/retentée
     * moves : déplacements, fusions, dispersions, pillages d'ordres,
       changements de contrôle
     * nobles : chevauchées (déplacements de nobles), CAPTURES, libérations
     * winter (P1.6) : investissements acceptés/rejetés (avec raison),
       conservation 50 %, rapatriement, capitale désignée
    - MVP : rapport GLOBAL (hotseat, tout le monde voit tout, vision T0) ;
      le filtrage par joueur et la divulgation différée des événements
      viennent en P2.2 — la structure ne doit PAS empêcher ce filtrage
      futur (sections typées par événement)

3. ENDPOINTS DEV (cmd/server, état en MÉMOIRE — pas de persistance) :
   - GET /api/map — map.json (existe depuis P1.2, inchangé)
   - POST /api/game — { seed, players } → crée la partie en mémoire (re-set)
     ; au démarrage, le serveur crée une partie par défaut (seed/players via
     flags ou env : SEED, PLAYERS) pour que GET /api/map fonctionne sans
     appel préalable
- GET /api/state — state.json : la couche dynamique (architecture §5) —
      par territoire : owner, resources, troops (id, matricule, owner),
      infrastructures (type, level, owner), contrôle ; pas d'asOf au MVP
    - POST /api/orders — { chains, winter } (format du §1) → ResolveTurn →
      { report, state } (le nouveau state.json en réponse) ; parsing invalide
      → 400 avec numéro de ligne ; ordres d'hiver hors hiver → 400 ; chaînes
      soumises EN hiver → 400 (trêve : seuls les ordres d'hiver)
   - POST /api/reset — recrée la partie par défaut (dev convenience)

4. FRONT (web/) — boucle locale hotseat, fonctionnelle (P3.4 polira) :
   - App : sélecteur de joueur (P1, P2...), la carte (MapViewer branché sur
     GET /api/map + GET /api/state — les fixtures statiques de P0.3 sont
     remplacées par l'API), panneau d'ordres (textarea : une chaîne par
     noble — en-tête + lignes, ou lignes d'hiver selon la saison), bouton
     "Résoudre le tour" → POST /api/orders → affichage du TurnReport
     (sections : combat, ravitaillement, hiver — lisible, tableaux simples)
   - Vite proxy vers le serveur Go (port 8080 par défaut, configurables) ;
     l'état de la saison courante vient du header du rapport ou d'un champ
     du state.json (ajoute season au state.json si nécessaire, documente)
- Rendu des stocks, troupes et infrastructures sur la carte (positions,
      nombres) ; rafraîchissement après résolution

5. TESTS :
   - internal/engine/game_test.go :

     * ResolveTurn : cycle complet des saisons (P→É→A→H→P), turn++ au

* ANNÉE COMPLÈTE multi-joueurs (2 joueurs) : ordres par saison

   - DÉTERMINISME : deux simulations d'une année complète (même seed, mêmes
```
