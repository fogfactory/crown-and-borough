```

troupe/armée, villages, nommage communes, géométrie/graphe v2, règles
vivrières, état d'exemple + endpoint dev /api/state (P1.2f). La génération

PROBLÈME DE MODÉLISATION constaté en exécutant P1.2f : les troupes sont
des entités individuelles (models.Troop {id, matricule, owner, territory},
TerritoryState.troops []TroopID) mais n'ont AUCUNE caractérisation
individuelle dans le jeu. Ce dont le jeu a besoin : au plus UNE armée par
territoire, chaque armée ayant un OWNER et une TAILLE (le nombre de troupes
qui la composent). La jonction (P1.4) fusionnera deux armées en
ADDITIONNANT leurs tailles ; la dispersion (P1.4) disjoindra une armée en
plusieurs, en RÉPARTISSANT ses troupes (tailles). Les ordres et le front
interagissent avec les armées PAR TERRITOIRE, jamais par id d'armée : la
position de l'armée est son adresse (afficher une chaîne d'ordres en cours
se limite à la partie de la chaîne à partir de la case de l'armée). La
caractérisation par troupe (matricule, troupes spécialisées) est DIFFÉRÉE :
le modèle conserve une entité Army avec ID pour permettre son évolution
ultérieure, sans transporter de champ par troupe.

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais ; contenu de jeu en français.

     (retiré par P1.2a) revient pour les armées ; corriger le commentaire
     d'entities.go qui annonce "A* ids are retired".

     aucune armée) — AU PLUS UNE armée par territoire, par construction.
   - Validate() : §5 réécrit (ids uniques ; owner existant ; territoire
     existant ; Size >= 1 ; double indexation : le territoire désigné par

     §8 : remplace le contrôle de liste de troupes par la vérification du
     pointeur Army (existant, territoire cohérent).
   - Note de départage (commentaire sur Army) : deux armées de même taille
     se départagent par le code trigramme du TERRITOIRE où elles se

   - models_test.go : constructions "A1".., sizes, round-trip JSON avec
     "armies"/"army", cas d'erreur adaptés (armée de size 0, indexation
```
