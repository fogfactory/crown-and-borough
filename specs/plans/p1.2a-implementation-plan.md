# Plan P1.2a — Refactoring terminologique troupe/armée

Brief d'exécution autonome pour un modèle d'implémentation.

## Contexte

P1.1 (modèles), P1.2 (génération de carte) et le front React (`web/src`) existent. Le prompt P1.2a
change la nomenclature du jeu : « troupe » = l'unité individuelle de force (l'ancien
`models.Army`), « armée » = le GROUPE de troupes sur une même case (l'ancien « pile », sans type
dédié). En anglais (le code) : `troop` = l'unité, `army` = le groupe. La convention d'identifiant
des unités passe de `"A1"` à `"TR1"` (« A* » abandonné car « armée » désigne désormais le groupe ;
« T » est réservé aux territoires). Le seul ordre qui change : `R A` → `R T` (recruter une troupe).
Le prompt source est `specs/prompts/p1.2a-vocabulaire-troupe-armee.md` — lire ce fichier en entier
avant de commencer (table de substitution obligatoire, §1 §2 §3).

Règles absolues :

- Code exclusivement en anglais ; seules les chaînes de contenu de jeu sont en français.
- Aucune règle de jeu modifiée : diff des specs = vocabulaire uniquement, `R A` → `R T` excepté.
- « armée »/`army` conservés là où le sens GROUPE est déjà présent (ex. « Armée sans chaîne »,
  ordres O/K portés par la pile).
- La présente tâche est la SEULE autorisée à réécrire les specs/prompts listés, et uniquement
  pour la substitution de vocabulaire.
- Ne rien commiter.

## Difficulté et modèle recommandé

Difficulté **2/5** — refactoring mécanique sans changement de règles, mais volumineux (≈ 2 000
occurrences dans 19 fichiers de specs + ~150 dans le code). Le risque est l'INCOHÉRENCE : une
occurrence oubliée (ex. `slice(1)` du front, `"armies":[]` d'un test, `"A9"` d'un cas d'erreur) ou
un renommage abusif (`XXX A YYY`, ordres d'hiver). Modèle à application rigoureuse conseillé ;
vérifications finales automatisées (§8) non négociables.

## Décisions de conception (à appliquer et documenter)

1. **`Army → Troop`, `ArmyID → TroopID`** : champs (ID, Matricule, OwnerID, TerritoryID) et JSON
   tags (`"id"`, `"matricule"`, `"owner"`, `"territory"`) inchangés.
2. **Convention d'identifiants** : troupes `"TR1"`, `"TR2"`… (construites comme `"TR%d"`,
   aligné sur `models.ArmyID`/`TroopID`); historiquement `"A1"`, `"A2"`, `"A9"` dans les tests →
   `"TR1"`, `"TR2"`, `"TR9"`. Documenter dans le commentaire d'entêtes de `entities.go` :
   territoires `"T01"`, nobles `"N1"`, troupes `"TR1"` ; « T » réservé aux territoires, donc pas de
   préfixe « T » pour les troupes.
3. **`GameState.Armies []Army` → `Troops []Troop`** (json `"troops"`) ;
   `TerritoryState.Armies []ArmyID` → `Troops []TroopID` (json `"troops"`).
4. **Helper locale** `seenArmies` → `seenTroops` (dans `Validate`, section 8).
5. **Commentaires du code** : le mot `army`/`armée` restera employé au sens NOUVEAU (le groupe)
   quand le contexte l'exige (ex. famine « starves the largest piles » → « starves the largest
   armies ») ; sinon « troop ». En français, « pile » disparaît partout.
6. **Les ordres `XXX A YYY`, S/H/J/P/D/O/K et tous les ordres d'hiver sauf `R A`** sont intouchés.
   Seul `R A` → `R T` (recruter une **Troupe**).
7. **Docs** : substitution systématique « pile (groupe) » → « armée », « armée (unité) » → «
   troupe », telle que définie dans la table du prompt ; reformulation minimale pour rester
   lisible, sans changer les règles.
