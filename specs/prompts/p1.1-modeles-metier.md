# Prompt P1.1 — Modèles métier Go

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le squelette Go existe (cmd/server, internal/{api,engine,db,models} vides,
assets/ avec les CSV de communes, prénoms et qualificatifs + loader Go).
Références : specs/gdd.md (règles) et specs/architecture.md (section
"Contrats Serveur → Front : map.json / state.json").

Tâche : définir les structures de données métier dans internal/models/.
C'est le socle du moteur : pas de dépendance web, pas d'ORM, Go pur + stdlib
(JSON tags pour la sérialisation). Les ordres (types, chaînes) et le moteur
de résolution arrivent dans des tâches ultérieures (P1.3, P1.4) : ne les
implémente pas, mais prévois la place pour eux.

RÈGLE DE CODE : le code est EXCLUSIVEMENT en anglais (identifiants, noms de
fichiers, commentaires, messages d'erreur/log, valeurs d'enums). Seules les
chaînes de contenu de jeu (noms de communes, territoires, prénoms) sont en
français, langue du jeu.

1. Enums (chaînes, typées, avec méthodes de validation) — valeurs en ANGLAIS :
   - Terrain : plain | forest | hill | mountain | swamp
     (aligné sur les valeurs de assets/qualificatifs.csv)
   - Season : spring | summer | autumn | winter
   - InfraType : mill | post_relay | watchtower | supply_depot | castle

2. Entités :
   - Player : ID, Name, Color ; Capitale = un Territoire (lieu-dit)
   - Territory : ID (interne), Code (trigramme territoire, ex. FROS), Name,
     Terrain, IsLieuDit, Adjacencies []TerritoryID (graphe d'adjacence
     franchissable). Pas de géométrie (points SVG) : elle arrive en P1.2
     dans le générateur de carte, hors modèles.
   - Army : ID, Matricule (numéro d'armée, utilisé pour le départage famine
     du GDD), OwnerID, TerritoryID
   - Noble : ID, Code (trigramme prénom), Name, OwnerID, LocationID
     (territoire où il se trouve)
   - Infrastructure : ID, Type (InfraType), Level (int, ≥ 1, utile pour le
     moulin +1 R/niveau), OwnerID, TerritoryID
   - TerritoryState (couche dynamique par territoire) : OwnerID (contrôle),
     Resources (stock R), Armies []ArmyID, Infrastructures []InfraID

3. GameState :
   - ID, Seed (string, pour la génération de carte), Turn (int), Season,
     Players []Player, Territories []Territory, Nobles []Noble,
     Armies []Army, Infrastructures []Infrastructure,
     TerritoryStates map[TerritoryID]TerritoryState
   - Méthode NewGame(seed, players, mapData...) prévue mais NON implémentée
     (la génération de carte est P1.2) ; fournis en revanche :
     - un constructeur NewGameState() + accesseurs/types utiles (ex.
       Type TerritoryID, ArmyID, NobleID, InfraID = string — pas d'UUID
       encore, des identifiants courts lisibles "T01", "A1", "N1" suffisent)
     - des helpers de validation (terrain/season/infra valides, ID uniques,
       adjacences symétriques, armée/noble/référant un territoire existant)
     - la sérialisation JSON de GameState (round-trip fiable, sans perte)

4. Famine / fraîcheur : prévois dans les types les champs nécessaires
   (asOf par territoire pour la vision T-x viendra en P2 — ne l'ajoute pas
   encore aux structures si ce n'est pas nécessaire au moteur).

5. Tests unitaires (internal/models/models_test.go) :
   - enums : valeurs valides/invalides
   - validation : IDs dupliqués, adjacences non symétriques, références
     inexistantes → erreurs explicites
   - JSON round-trip d'un GameState complet (créé à la main en test)
   - invariants des codes : 4 lettres pour Territory, 3 pour Noble

Critères d'acceptation :
- make test passe (tous les tests modèles verts)
- make vet passe
- Aucune dépendance tierce ajoutée (stdlib uniquement)
- Les structures sont commentées en lien avec le GDD (ex. matricule pour le
  départage famine) mais SANS code du moteur

Ne commite pas : je m'en charge.
```
