# Plan P1.2b — Lieux-dits → Villages (infrastructure + villages neutres)

Brief d'exécution autonome pour un modèle d'implémentation.

## Contexte

P1.1 (modèles), P1.2 (génération de carte), P1.2a (vocabulaire troupe/armée) et le front React
(`web/src`) existent. Le prompt P1.2b supprime la notion de « lieu-dit » et introduit le VILLAGE
comme infrastructure :
- Le flag `lieuDit` disparaît partout (modèles, map.json, front, tests).
- Nouvelle infrastructure `village` (InfraType) : produit 2 rations/tour et sert d'ANCRE de
  ravitaillement, comme un château (production détaillée en P1.2e).
- Les villages sont NON constructibles au MVP (réservé) : seuls des villages NEUTRES apparaissent
  sur la carte initiale.
- Les infrastructures N'ONT PAS DE PROPRIÉTAIRE : seul le territoire porte un propriétaire.
  `Infrastructure.OwnerID` est supprimé.
- Construire un château sur un village le REPLACE (jamais deux structures par case).
- Une ligne de ravitaillement part du château OU village contrôlé le plus proche.

Le prompt source est `specs/prompts/p1.2b-lieux-dits-villages.md` — lire ce fichier en entier
avant de commencer.

Règles absolues :

- Code exclusivement en anglais ; seules les chaînes de contenu de jeu sont en français.
- Aucune règle de jeu modifiée : diff des specs = substitution de vocabulaire + reformulation
  minimale, sans devancer P1.2e (production/règles de ravitaillement détaillées là-bas).
- La présente tâche est la SEULE autorisée à réécrire les specs/prompts listés.
- Ne rien commiter.

## Difficulté et modèle recommandé

Difficulté **2,5/5** — refactoring mécanique + un algorithme simple (répartition greedy des
villages) + volume documentaire. Le risque est l'INCOHÉRENCE (une occurrence de `lieuDit`
oubliée). Vérifications finales automatisées (§ Vérifications) non négociables.

## Décisions de conception (à appliquer et documenter)

1. **`assignVillages` — greedy max-min, TOUS les terrains éligibles** (décision actée : ne PAS
   exclure montagne/marais) :
   - Signature : `assignVillages(rng *rand.Rand, terrain []models.Terrain,
     centroids [][2]float64, count int) ([]bool, error)`.
   - Éligibles = tous les sites (aucune exclusion de terrain).
   - Premier village tiré uniformément via le RNG parmi les éligibles ; chaque suivant = le site
     éligible maximisant la distance euclidienne (au carré, centroïdes) au village déjà placé le
     plus proche ; départage déterministe : plus petit index de site.
   - Erreur si `len(sites) < count` (contrainte `count ≤ len(sites)`).
   - Phase RNG `"lieudit"` → `"village"`.
2. **Seuil de répartition (test)** : distance minimale inter-villages ≥ **15 % de la diagonale
   du viewport** (1000×700 → ≈ 183 px), asserté sur les 5 seeds de test. Vérification empirique
   pendant l'implémentation ; si un seed échoue, critère équivalent documenté (borne réellement
   atteinte par le greedy) plutôt que complexifier l'algo.
3. **Valeur dev** : `VillageCount = 5` en constante dans `cmd/server/main.go`, commentaire
   renvoyant à P1.2d (`?players=N`, `VillageCount = joueurs + 1`).
4. **Validation transitoire des codes (modèles)** : `isCode(code, 3) || isCode(code, 4)` pour
   tout territoire, commentaire `TRANSITIONAL (P1.2b)` → `P1.2c` restore "3 letters everywhere".
5. **Fixture d'état** : IDs des territoires village du seed dev extraits via
   `curl /api/map | jq` après implémentation, écrits en dur dans `fixtures/state.ts`
   (`owner: null, resources: 0, troops: [], infrastructures: [{type:'village', level:1}]`) +
   commentaire "transitoire, P1.2f remplacera ce stub". Requis par le critère « les villages
   s'affichent via la couche état (fixture) ».
6. **Marqueur ressources ×N** (MapViewer) : conservé, gate `territory.lieuDit &&` remplacée par
   `territoryState.resources > 0` seul.
7. **Légende** : entrée "Village" (glyph maison inline SVG) + `<title>Village</title>` dans le
   marqueur + aria-label du groupe codes → "Codes des territoires".
