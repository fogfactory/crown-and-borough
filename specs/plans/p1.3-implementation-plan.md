# Plan d'implementation P1.3 - Parser des chaines d'ordres

Brief d'execution autonome pour une future implementation. Ce document est le seul
fichier a creer dans la session de planification courante : aucune etape ci-dessous
n'est executee ici.

## Contexte

Le prompt source est `specs/prompts/p1.3-ordres-chaines.md`. Les modeles metier,
la carte et un etat de demonstration existent deja. Le modele courant ne contient
pas d'entite `Troop` : `models.Army` est l'unique entite de force presente sur un
territoire et son champ `Size` represente le nombre abstrait de troupes qu'elle
contient (P1.2g). Les chaines doivent donc etre portees par `Army`/`ArmyID`, jamais
par un `TroopID` inexistant.

References principales :

- `specs/prompts/p1.3-ordres-chaines.md` : perimetre, grammaire, validation et reception ;
- `specs/architecture.md` section 5 pour `state.json` et section 6 pour la syntaxe ;
- `specs/gdd.md` sections 4, 5 et 6 pour les armees, les nobles et les ordres ;
- `specs/prompts/p1.4-resolution-combat.md` pour la future progression simultanee ;
- `specs/roadmap.md` pour l'ordonnancement des paliers ;
- `specs/plans/p1.2g-implementation-plan.md` pour la convention Army/ArmyID.

## Perimetre

La future implementation couvre :

- le modele serialisable des ordres et des chaines ;
- le statut de captivite des nobles necessaire a la reception ;
- le parsing texte avec erreurs collectees et numero de ligne ;
- la validation statique pure des chaines ;
- l'assignation directe d'une chaine a l'armee receptrice ;
- le remplacement, la capacite d'emission et les verifications de reception ;
- le round-trip JSON de `GameState` ;
- l'exposition non filtree des chaines dans l'endpoint dev `/api/state` ;
- la documentation de l'interface future de resolution.

La future implementation ne couvre pas :

- `Resolve` et la resolution simultanee des combats, retraites, jonctions ou dispersions ;
- la progression `single`/`loop` apres execution ;
- la transmission differee par messager (P2.3) ;
- les projections de mouvements et le filtrage prive par joueur (P2.2) ;
- la fuite d'information par les nobles otages (nouveau prompt P2.2a) ;
- l'interface front d'affichage des chaines, qui est rattachee a P1.7 ;
- un endpoint HTTP de soumission des ordres.

## Difficultes et risques

Difficulte **4/5** : le code reste stdlib-only, mais plusieurs niveaux de
validation doivent rester distincts. Le risque principal est de faire entrer dans
le parser ou `ValidateChain` des regles qui ne sont connues qu'a l'execution.

Les frontieres a respecter sont :

- **Parser** : syntaxe, casse, commentaires, parenthese, arite et resolution des
  codes vers les identifiants du jeu ;
- **Validation statique** : references, adjacences, structure et contraintes
  intrinseques a l'ordre ;
- **Reception** : armee presente, proprietaire, capacite, taille reelle de l'armee
  et couverture des nobles au moment de l'assignation ;
- **Execution P1.4** : position devenue fausse, case occupee, combat, infrastructure
  absente et autres conditions du monde.

Le `GameState` est construit a la fois par `NewGameState` et par des litteraux dans
`demo` et les tests. L'ajout de champs obligatoires devra donc mettre a jour tous
ces constructeurs.

## Decisions de conception

### 1. Army est l'entite de commande

`Army` reste l'entite de force, avec `Size` comme nombre de troupes abstraites.
Les champs de chaine utilisent `ArmyID` :

- `Army.ChainID *ChainID` : nil signifie "Sans Ordre" ;
- `Chain.ArmyID ArmyID` : armee porteuse de la chaine ;
- `Order.ArmyID ArmyID` : armee d'application, vide uniquement pendant le parsing
  avant reception puis renseigne lors de l'assignation.

La formulation "la troupe au plus petit matricule represente son armee" est
supprimee des specs et remplacee par "la chaine est portee par l'armee unique
presente sur le territoire de reception".

### 2. Noble : LocationID + statut

`Noble.LocationID` est conserve. Il permet de retrouver l'armee chevauchee car le
modele impose au plus une armee par territoire. Aucun `Noble.ArmyID` n'est ajoute.

Le modele ajoute `NobleStatus` :

- `free` : libre ;
- `hostage` : otage, etat de prisonnier par defaut ;
- `dungeon` : au cachot.

En code et dans les docs, `hostage` et `dungeon` forment l'ensemble "prisoner".
Le geolier est derive du proprietaire de l'armee du `LocationID`, et n'est pas
duplique dans `Noble`.

Cette representation conserve le cas limite prevu par le GDD : une armee peut etre
detruite sur une case vide ou alliee et le noble rester seul sur la case. `Validate`
verifie donc le statut et le territoire, mais ne rend pas impossible ce cas limite
en exigeant toujours un pointeur d'armee.

`Noble.LastEmissionTurn int` est ajoute pour faire respecter "une emission par
noble et par tour" meme lorsqu'une nouvelle chaine remplace et supprime l'ancienne.
La valeur zero signifie qu'aucune emission n'a encore ete enregistree.

### 3. Modele des ordres

Creer `internal/models/orders.go` avec :

- `ChainID string` et `OrderID string` comme types nommes ;
- `TerritoryCode string` et `NobleCode string` pour respecter le contrat
  `NobleAssignments` sans changer les champs `Territory.Code` et `Noble.Code`
  existants ;
- `OrderType` : `attack`, `support`, `hold`, `join`, `pillage`, `disperse`,
  `hostage`, `dungeon` ;
- `LiaisonMode` : `single`, `loop` ;
- `Order` ;
- `Chain`.

Le modele recommande est :

```go
type Order struct {
    // ID is assigned by the parser and is unique within its chain.
    ID               OrderID
    // Type is parsed from the order symbol and consumed by validation and P1.4.
    Type             OrderType
    // ArmyID is empty after parsing and set to the receiving army by AssignChain.
    ArmyID           ArmyID
    // PositionID comes from the explicit position code and is the required
    // position when this order is executed.
    PositionID       TerritoryID
    // TargetIDs come from territory codes in A, S, J and D orders.
    TargetIDs        []TerritoryID
    // NobleTargetIDs come from the noble code targeted by O or K orders.
    NobleTargetIDs   []NobleID
    // NobleAssignments comes from D asterisks and is consumed when dispersion
    // assigns nobles to destinations.
    NobleAssignments map[TerritoryCode][]NobleCode
    // Liaison comes from the order line parentheses and is consumed by P1.4
    // progression after the order outcome is known.
    Liaison          LiaisonMode
}

type Chain struct {
    // ID is allocated by AssignChain and remains stable while the chain exists.
    ID           ChainID
    // NobleID comes from the header noble code and identifies the emitter.
    NobleID      NobleID
    // ArmyID is empty after parsing and set by AssignChain for the receiving army.
    ArmyID       ArmyID
    // Orders are parsed in source order and later progressed by CurrentIndex.
    Orders       []Order
    // CurrentIndex is read and advanced by P1.4 after resolving the current order.
    CurrentIndex int
}
```

The actual Go declarations must retain equivalent English field comments, even if
the final layout or JSON tags differ from this planning excerpt. Each comment must
state the field's source (parser, header, explicit code, or reception) and its
consumer (validation, `AssignChain`, state projection, or P1.4 resolution) where
that distinction matters.

`NobleTargetIDs` est l'ajout necessaire pour corriger une ambiguite du prompt :
`TargetIDs []TerritoryID` ne peut pas representer la cible noble des ordres O/K.
Les ordres territoriaux utilisent `TargetIDs`; O/K utilisent un unique
`NobleTargetIDs` resolu a partir du trigramme.

`NobleAssignments` conserve les codes pour refleter la syntaxe et le round-trip :
la valeur `NobleCode("*")` signifie "tous les nobles restants". Une destination
peut etre repetee dans `TargetIDs` pour representer plusieurs troupes qui la
rejoignent ; la map d'assignation est fusionnee par code de destination.
Les assignations explicites sont prises en compte avant l'expansion du joker.
Un seul joker par ordre D est retenu comme regle de reception ; plusieurs jokers
sont une erreur de validation, car le second n'aurait plus de notion deterministe
de nobles "restants".

Les tags JSON seront explicites et en camelCase conforme aux modeles existants :
`id`, `type`, `army`, `position`, `targets`, `nobleTargets`,
`nobleAssignments`, `liaison`, `noble`, `orders`, `currentIndex`.
Les champs temporaires non renseignes avant reception peuvent etre omis du JSON,
mais toute chaine stockee dans `GameState` doit etre complete et serialisable.

### 4. Identifiants et compteur de chaines

Le parser attribue des IDs d'ordre locaux a la chaine : `O1`, `O2`, etc. La
reception attribue un ID global de chaine `C1`, `C2`, etc. Comme une chaine brisee
ou consommee sera supprimee en P1.4, `len(GameState.Chains)` ne suffit pas pour
garantir l'unicite. Ajouter `GameState.NextChainID int`, initialise a `1`, et le
persister dans le `GameState` interne.

`CurrentIndex` vaut zero lors de la reception. Une chaine assignee doit avoir au
moins un ordre et un index compris dans ses ordres ; une chaine consommee est
supprimee par P1.4 plutot que stockee avec un index egal a la longueur.

### 5. Chaines dans GameState et state.json

Ajouter `GameState.Chains []Chain` et l'initialiser a une slice vide dans les
constructeurs. Le lien inverse `Army.ChainID` permet de determiner "Sans Ordre"
sans ajouter de champ de statut d'armee.

L'endpoint dev `/api/state` n'a pas encore d'identite joueur : `players` indique le
nombre de joueurs, pas le joueur connecte. La projection dev expose donc toutes les
chaines, sans filtrage. Cette exception est explicitement documentee et ne fixe pas
la future politique privee de P2.2/P3.2.

Le DTO projette la chaine sous l'armee du territoire :

```json
{
  "army": {
    "owner": "P1",
    "size": 2,
    "chain": {
      "noble": "HUG",
      "currentIndex": 0,
      "orders": [
        {
          "type": "attack",
          "position": "ROS",
          "targets": ["BOI"],
          "liaison": "single"
        }
      ]
    }
  }
}
```

`chain` vaut `null` quand l'armee n'a pas de chaine. Les IDs internes d'armee et
de chaine ne sont pas exposes dans `StateView`; l'adressage public reste le
territoire. Les ordres de la vue utilisent les codes de territoire et de noble,
et conservent les `nobleAssignments` pour D.

Le DTO des nobles ajoute au minimum `code` et `status`, necessaires pour adresser
les nobles et rendre leur etat de captivite explicite.

### 6. Purete et atomicite

`ValidateChain` ne modifie ni le jeu ni la chaine. `AssignChain` ne modifie rien
tant que toutes les validations de reception ne sont pas passees : la chaine
ancienne est retiree et le nouvel index inverse est installe dans une seule phase
de commit.

Les erreurs de soumission sont structurees, en anglais, et peuvent etre testees
avec `errors.Is` pour les categories principales. Une erreur de validation ne doit
jamais laisser une chaine partiellement remplacee.

### 3. Parser texte

Fichier : `internal/engine/orders/parser.go`.

Signature :

```go
func ParseChain(text string, game *models.GameState) (models.Chain, []ParseError)
```

Regles d'implementation :

- conserver les numeros de ligne originaux, y compris les lignes vides et les
  commentaires ;
- retirer tout ce qui suit `#`, trim, normaliser en majuscules et ignorer les lignes
  devenues vides ;
- exiger comme premier contenu un en-tete `NOB` optionnellement suivi d'un commentaire ;
- resoudre le trigramme de l'en-tete vers `Chain.NobleID` ;
- distinguer `bad_header`, `no_header` et `noble_not_found` ;
- accepter les espaces multiples et les parentheses autour d'une ligne complete ;
- convertir `(ordre)` en `LiaisonModeLoop` et une ligne non parenthesee en

- signaler toute parenthese mal equilibree par `unclosed_parenthesis` ;
- parser `A`, `J`, `S`, `H`, `P`, `O`, `K` et `D` avec leurs arites exactes ;
- resoudre les codes de territoire en `TerritoryID` et les codes nobles en
  `NobleID` sans faire ici les tests d'adjacence ;
- parser le soutien defensif `XXX S YYY` et le soutien offensif
  `XXX S YYY - ZZZ` ;
- parser D avec une destination par troupe abstraite, en conservant les repetitions ;
- parser les suffixes d'asterisque `XXX*`, `XXX*JEA`, `XXX*JEA*ANN` ;
- rejeter `*` sans code de destination, un suffixe mal forme ou un code inconnu ;
- attribuer `O1..On` aux ordres valides dans l'ordre d'apparition ;
- collecter les erreurs de toutes les lignes au lieu de s'arreter a la premiere ;
- ne pas produire d'`ArmyID` ni de `ChainID` definitifs avant reception ;
- retourner les ordres syntaxiquement valides avec les erreurs, afin que l'appelant
  puisse afficher toutes les fautes mais interdise l'assignation tant que la liste
  d'erreurs n'est pas vide.


### 4. Validation statique

Fichier : `internal/engine/orders/validate.go`.

Signature :

```go
func ValidateChain(game *models.GameState, chain models.Chain) []ValidationError
```

Verifications :

- noble de l'en-tete existant ;
- positions, cibles territoriales et cibles nobles existantes ;
- A/J : destination adjacente a `PositionID` ;
- soutien defensif : `YYY` adjacent a `XXX` et `YYY != XXX` ;
- soutien offensif : `ZZZ` adjacent a `XXX` et `YYY` adjacent a `ZZZ` ;
- D : chaque destination adjacente ou egale a la position ;
- J present uniquement comme dernier ordre ;
- H/P sans cible territoriale supplementaire ;
- O/K avec exactement une cible noble resolue ;
- D avec assignments visant une destination declaree ;
- noble assigne au plus une fois dans le meme D ;
- au plus un joker D ;
- codes nobles des assignments existants.

`ValidateChain` ne verifie pas les faits qui peuvent changer avant l'execution :
case libre ou occupee, mouvement effectif de l'armee, presence d'une infrastructure,
position courante des ordres suivants, resultat d'un combat ou existence future de
la cible O/K. Si une chaine est deja liee a une armee et qu'un ordre O/K porte sur
la position courante de cette armee, la relation "noble prisonnier co-localise et
detenu par cette armee" peut etre controlee a la reception ; le meme controle sur
un ordre futur reste du ressort de P1.4.



### 5. Reception et remplacement

Fichier : `internal/engine/orders/assign.go`.

Signature :

```go
func AssignChain(game *models.GameState, chain models.Chain) error
```

Ordre des controles avant mutation :

1. verifier les invariants de forme et appeler la validation statique ;
2. retrouver le noble de l'en-tete ;
3. refuser `hostage` et `dungeon` comme emetteur ;
4. refuser si `LastEmissionTurn == game.Turn` ;
5. lire `chain.Orders[0].PositionID`, y compris H/P, comme position de reception ;
6. trouver sur cette case une armee appartenant a `Noble.OwnerID` ; une armee
   absente ou etrangere donne une erreur propre ;
7. pour chaque ordre D, comparer `len(TargetIDs)` a `Army.Size` au moment de la
   reception, repetitions comprises ;
8. pour chaque D, verifier que tous les nobles dont `LocationID` est la case de
   l'armee sont couverts exactement une fois par assignment explicite ou expansion
   du joker, prisonniers compris ;
9. pour un ordre O/K executable immediatement sur la position de reception, exiger
   que la cible soit non libre, co-localisee et detenue par le proprietaire de
   l'armee ; un ordre O/K sur une position future est revalide par P1.4 ;
10. seulement apres succes, supprimer la chaine precedente de cette armee, allouer
     `C<NextChainID>`, incrementer le compteur, remplir `Chain.ArmyID` et chaque
    `Order.ArmyID`, mettre `Army.ChainID`, append la chaine et enregistrer
    `Noble.LastEmissionTurn = game.Turn`.

Une erreur a une etape quelconque ne modifie ni l'ancienne chaine, ni le compteur,
ni la capacite du noble.
