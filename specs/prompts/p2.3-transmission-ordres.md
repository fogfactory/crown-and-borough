# Prompt P2.3 — Transmission différée des ordres (messagers)

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Le moteur existe (P1.4/P1.5/P1.6 : résolution, ravitaillement, hiver ; P2.1 :
soutien automatique ; P2.2 : vision T-x par joueur), le cycle de jeu et l'API
dev (P1.7), le parser (P1.3 : réception instantanée au MVP).
Références : specs/gdd.md (§4 Ordres par Messager, §3 Vitesse des messagers)
et specs/architecture.md (§6 Réception de la chaîne).

PÉRIMÈTRE : les chaînes ne sont PLUS reçues instantanément : elles voyagent
de la Capitale à l'armée ciblée à la vitesse du terrain (les mêmes coûts que
P2.2). L'armée poursuit son ANCIENNE chaîne tant que la nouvelle ne l'a pas
atteinte. Interception des chaînes par l'ennemi. La vision T-x (P2.2) reste
telle quelle. P3 (API réelle, auth, persistance) HORS périmètre.

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. CHANGEMENT DE SÉMANTIQUE (remplace la réception instantanée de P1.3) :
   - Une chaîne soumise (P1.7 /api/orders) n'est PLUS assignée immédiatement :
     elle devient un MESSAGE (messager) en attente de voyage
   - Point de DÉPART : la CAPITALE du joueur émetteur (GDD §4 : "émis depuis
     la Capitale"). Joueur sans capitale (aucun château) → soumission
     REFUSÉE (erreur explicite)
   - CIBLE : l'armée visée (celle qui était sur la position de la 1re ligne
     à l'émission) — le messager la POURSUIT si elle bouge
   - L'émission consomme la capacité du noble (1 émission/tour) au moment de
     la soumission, comme avant
   - L'armée EXÉCUTE son ancienne chaîne tant que le messager ne l'a pas
     atteinte (progression normale des chaînes pendant le voyage)

2. VOYAGE (internal/engine, dans le cycle de jeu P1.7) :
   - Modèle : GameState.PendingOrders []PendingOrder { ID, PlayerID,
     NobleCode, Chain, TargetArmyID, PositionID (case du messager),
     BudgetRemaining float64 }
   - À chaque résolution de tour, AVANT l'exécution des ordres :
     (1) chaque messager avance de 1 tour de trajet — budget = 1.0,
     avance le long du PLUS COURT CHEMIN (Dijkstra, départage ID croissant)
     vers la position COURANTE de l'armée cible, en consommant le coût des
     cases traversées (plaine/route 0,5 | forêt/colline 1 | montagne/
     marécage 2 | relais : coût divisé par 2) ; si le budget le permet,
     il enchaîne les cases ; il s'arrête dès que le budget est épuisé
     (2) ARRIVÉE : messager sur la case de l'armée cible → la chaîne EST
     reçue : elle remplace la chaîne de l'armée (règles de P1.3 — position
     de la 1re ligne NON revérifiée : le messager a suivi l'armée) ; la
     chaîne reçue s'exécute à partir du tour SUIVANT
     (3) deux messagers arrivant le même tour sur la même armée → la chaîne
     émise le PLUS RÉCEMMENT gagne (départage : ordre d'émission)
   - Le messager s'arrête : armée DÉTRUITE (combat) → ordre perdu ; armée
     PRISONNIÈRE ? — impossible (seuls les nobles sont prisonniers) ; armée
     qui s'éloigne toujours → le messager la poursuit indéfiniment (cas
     documenté : l'armée garde son ancienne chaîne tant que le messager ne
     l'a pas rattrapée)

3. INTERCEPTION (tests du roadmap : "interception de chaîne") :
   - Un messager qui tente d'ENTRER sur une case CONTRÔLÉE par un ENNEMI du
     joueur émetteur (TerritoryState.OwnerID ≠ émetteur et ≠ nil) est
     INTERCEPTÉ : l'ordre est DÉTRUIT (la chaîne n'arrive jamais)
   - Un messager qui se trouve sur une case devenue ennemie au début de son
     avance est intercepté immédiatement
   - L'intercepteur reçoit un événement InterceptionEvent (messager détruit,
     armée ciblée) — au MVP il N'APPREND PAS le contenu de la chaîne (choix
     documenté : savoir qu'un ordre passait est déjà de l'information)

4. EVENTS : PendingOrderEvent (émission : noble, cible, départ),
   OrderArrivalEvent (armée, chaîne reçue, remplacement),
   InterceptionEvent (messager, intercepteur, cible) — intégrés au
   TurnReport (P1.7, section orders) ; pas de formatage

5. IMPACT API DEV (P1.7) : POST /api/orders crée les PendingOrders (plus
   d'assignation directe) ; l'état (state.json) expose les messagers en
   transit (position, cible, tour restant estimé) pour le debug (dev)

6. TESTS (internal/engine/messenger_test.go) :
   - DÉLAIS : capitale → armée à 2 cases de plaine (coût 1,0) → arrivée au
     tour suivant ; l'armée exécute SON ANCIENNE chaîne pendant le voyage
     (progression vérifiée), la nouvelle chaîne s'exécute au tour d'après
   - Vitesses du terrain : forêt (1/tour) et montagne (2/tour) ralentissent
     ; relais de poste sur le chemin accélère (coût divisé par 2) ; route
     = plaine (0,5)
   - POURSUITE : l'armée bouge pendant le voyage → le messager la suit et
     la rattrape (arrivée sur sa nouvelle position) ; armée toujours plus
     loin → poursuite indéfinie, ancienne chaîne conservée
   - REPLACEMENT : arrivée → ancienne chaîne remplacée ; deux messagers le
     même tour → la chaîne émise le plus récemment gagne
   - INTERCEPTION : chemin traversant une case ennemie → intercepté, ordre
     perdu, événement chez l'intercepteur ; case devenue ennemie pendant le
     voyage → intercepté à la reprise du voyage ; armée détruite → ordre
     perdu (sans interception)
   - SOUISSION : joueur sans capitale → refus ; capacité noble inchangée
     (1 émission/tour)
   - DÉTERMINISME : deux simulations identiques → mêmes trajets, mêmes
     arrivées, mêmes interceptions ; cohérence (messagers sur des
     territoires existants, budget ∈ [0, 1))

Critères d'acceptation :

- La réception instantanée de P1.3 est remplacée proprement (le code de

- Les messagers vivent dans GameState (sérialisables JSON, round-trip)
- Le TurnReport expose les événements de messagers
```
