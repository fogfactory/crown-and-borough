# Prompt P1.3 — Ordres & chaînes de commandement

```
Tu travailles sur "Crown & Borough", un jeu de stratégie asynchrone par tours.
Les modèles métier existent (internal/models : GameState, Territory, Army,
Noble, enums), la génération de carte est en place (internal/engine/mapgen,
endpoint /api/map). Le moteur de RÉSOLUTION (mouvement, combat, retraites)
est la tâche P1.4 : ne l'implémente pas, mais conçois l'interface de sorte
qu'il s'y branche.
Références : specs/gdd.md (section 6) et specs/architecture.md
(SECTION 6 — "Format des chaînes d'ordres (texte)" : le format y est décrit
précisément, suis-le à la lettre).

Tâche : implémenter le PARSER des chaînes d'ordres texte et la sémantique
des chaînes dans internal/engine (package ordres ou engine).

RÈGLE DE CODE : code EXCLUSIVEMENT en anglais (identifiants, commentaires,
messages, enums). Seules les chaînes de contenu de jeu sont en français.

1. Format texte (décrit dans architecture.md §6, à implémenter tel quel) :
   - En-tête : code trigramme du noble émetteur (ex. "JEST # Jean d'Estaing",
     le reste après # est un commentaire)
   - Une ligne par ordre : CODE_FROM SYMBOLE [CODE_CIBLE...] [# commentaire]
     - Sans parenthèses = liaison SINGLE ; entouré de parenthèses = BOUCLE
       ("(ATL S NOR)" = boucle, "BRI A ATL" = single) — chaque transition a
       SA propre liaison
   - Insensible à la casse (normalisé en MAJUSCULES), lignes vides ignorées,
     codes valides vérifiés contre les assets/la carte, erreurs avec numéro
     de ligne et code d'erreur

2. Symboles et sémantique (cf. architecture.md §6, tableau complet) :
   - A : attaque/atteindre — déplacement vers case ADJACENTE (combat si
     occupée ; la résolution du combat est P1.4, ici on définit le contrat)
   - S : soutien — case ADJACENTE soutenue ; en boucle : soutient tant
     qu'une attaque cible la case, sort quand plus aucune attaque
   - H : maintien — pas de cible ; en boucle : garde indéfinie (chaîne en
     veille)
   - J : jonction/blocage — pas de cible (ou = FROM) ; l'armée verrouille sa
     case ; en boucle : veille indéfinie comme H
   - P : pillage — case ADJACENTE ciblée ; aucune infrastructure sur la cible
     → ordre INVALIDE (brise toujours) ; en boucle : retente jusqu'à
     destruction
   - D : dispersion — UNE cible par armée de la pile ; chaque destination
     doit être libre et non ciblée par une attaque ce tour (déplacement
     pacifique, pas une attaque) ; le territoire FROM est autorisé ; en
     boucle : retente jusqu'à résolution INTÉGRALE ; en single : la chaîne
     avance même si la dispersion est partielle

3. Modèle (internal/models) :
   - Order { ID, Type (OrderType), ArmyID, TargetIDs []TerritoryID,
     Liaison LiaisonMode } — LiaisonMode : single | loop, PORTÉ PAR L'ORDRE
     (plus par la chaîne)
   - Chain { ID, NobleID, ArmyID (fixé à la réception : voir point 4),
     Orders []Order, CurrentIndex int } — l'état "Sans Ordre" d'une armée =
     aucune chaîne référencée (PAS de champ ArmyStatus : army.ChainID nil
     suffit)
   - OrderType : attack | support | hold | join | pillage | disperse

4. Réception de la chaîne :
   - À la soumission (vision T0 au MVP ; la transmission différée est P2.3) :
     la chaîne est reçue par l'armée présente sur le territoire FROM de la
     PREMIÈRE ligne. Aucune armée sur ce territoire → erreur de soumission
     (pas d'armée, ou armée ennemie : hors scope pour l'instant, signaler
     proprement)
   - Le code FROM de chaque ligne est le territoire où l'armée doit se
     trouver quand CET ordre s'exécute : si ce n'est pas le cas au moment
     de l'exécution → FAILURE (single : brise ; loop : retente)

5. Progression (fonction pure, prête pour P1.4) :
   - AdvanceChain(game, chain, outcome) → (state, error), outcome ∈
     { success, failure, invalid }
   - success → CurrentIndex++ (et exécution de l'ordre ; si l'ordre était
     une dispersion partielle en single : avance quand même)
   - failure → single : chaîne brisée (armée Sans Ordre) ; loop : index
     inchangé (retentative au tour suivant)
   - invalid → brise IMMÉDIATEMENT dans les DEUX modes
   - Chaîne terminée (dernier ordre réussi) : chaîne consommée, armée Sans
     Ordre. Boucle sur le dernier ordre : veille indéfinie (H/J) ou
     retentative (A/S/P/D) selon l'ordre — cf. sémantique ci-dessus
   - Nouvel ordre reçu > chaîne existante : le nouvel ordre REMPLACE (la
     capacité noble limite les émissions)

6. Capacité des Nobles :
   - Un noble ne peut émettre ou modifier qu'UNE SEULE chaîne par tour ;
     une modification d'une chaîne existante compte comme une émission
   - Toute armée sans noble ne peut pas recevoir de chaîne

7. Parser (internal/engine, ex. orders.go ou package ordres) :
   - ParseChain(text string, game) → (Chain, []ParseError) : erreurs
     COLLECTÉES (toutes les lignes signalées), chaque erreur avec n° de
     ligne, type d'erreur (unknown_symbol, invalid_code, missing_target,
     too_many_targets, bad_header, no_header, noble_not_found...), message
     en anglais
   - Gère parenthèses, commentaires #, casse, espaces multiples, ligne vide
   - Tests exhaustifs du parser : exemples du format (architecture.md §6),
   cas limites (sans en-tête, symbole inconnu, code inexistant, cible
   manquante, D sans cible, parenthèse non fermée...)

8. Sérialisation : chaînes et ordres survivent au round-trip JSON de
   GameState (tests inclus).

9. Tests (internal/engine/orders_test.go ou équivalent) :
   - Parser : chaque règle du point 7, + les exemples exacts du format
   - Progression : O1→O2→O3 réussie ; single : échec de O1 → Sans Ordre ;
     échec de O2 après succès de O1 → idem ; loop : échec → retentative
     index inchangé puis succès → progression ; invalid dans les deux modes
   - Liaison MIXTE dans une même chaîne (O1 single, O2 loop, O3 single)
   - Sémantique par ordre : H boucle = garde (index figé, pas d'échec) ;
     J ; P sans infrastructure = invalid ; D partielle single vs intégrale
     loop (les "libre/non attaqué" sont des inputs du test : la résolution
     réelle viendra en P1.4)
   - Capacité noble : 1 émission + 1 modification/tour refusée
   - Réception : pas d'armée sur le FROM de la 1re ligne → erreur
   - JSON round-trip

Critères d'acceptation :
- make test passe ; make vet passe ; aucune dépendance tierce ajoutée
- L'interface de résolution est prête pour P1.4 : documente la signature
  prévue (ex. Resolve(game) produisant des outcomes par ordre) sans
  l'implémenter

Note : signale dans ta réponse finale toute évolution des specs nécessaire
(ne modifie pas les specs toi-même). Ne commite pas : je m'en charge.
```
